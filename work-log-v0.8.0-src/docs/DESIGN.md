# 设计决策与踩坑记录

这份文档记录**为什么这么写**、**刻意不做什么**，以及**踩过哪些坑**。
想改这个项目的话，先读这里能省很多时间 —— 有些看起来"可以优化"的地方是量过才不做的。

---

## 一、为什么是"共享文本看板"，不是每个 agent 一个日志文件

最直觉的做法是每个 agent 写自己的日志。问题是：**你要看 N 个文件才能知道发生了什么**，
而"谁卡住了"这个判断天然需要跨 agent 的比较（A 静默 60s 是不是异常？要看它平时多久写一次）。

一块看板带来三个直接好处：

1. **一次 `tail` 就是全局时间线。** 谁在等谁、谁说了什么、顺序如何，全在一个文件里。
2. **写操作天然需要串行化**，于是并发写问题被摊到明面上（`flock`），而不是藏在 N 个文件里。
3. **可以人肉修。** 它是纯文本、格式稳定，出问题了你直接编辑 —— 这比"修数据库"实际得多。

代价是：看板会变大，每轮扫描要读全文。所以做了解析优化（见「四」），
并且**坚持文本可反解**（`board.md` 能被解析回状态），换机器/换版本都不会丢历史。

## 二、为什么"等"要变成机制（`await`），而不是靠 agent 自觉

真实场景里最常见的一句指令是「你等 A 弄完再动手」。这句话在提示词里就是一句空话：
agent 要么干等（浪费一轮），要么假装等（其实自己编了个答案往下做）——**后者非常常见**。

所以把它变成机制：`await` 是一个**真的会阻塞的进程**，它有超时、有退出码、
有明确的三个出口（拿到 / 超时 / 对方已收工）。这样"等"就变成了可观测、可上报的事实，
而不是一句提示词里的礼貌请求。

配套的两条设计：

- **等待期间自动续心跳。** 否则"在等"会被看门狗判成"卡死" —— 一个诚实地等待的 agent
  反而被罚，这会让所有人学会假装在动。
- **对手已收工就立刻返回 `3`，不耗完超时。** 实测踩到过：对端早已写了「任务完成」，
  这边白等满 60s 且全程无告警。现在这种情况 0s 返回。

## 三、等待图：这个项目唯一"别人没有"的东西

看门狗只能看到**静默**。但有一类故障的心跳是全绿的：

> A 问了 B 一个问题，B 也问了 A 一个问题，然后**双方都在等对方回答**。
> 两个进程都活着、心跳都在续、日志很干净 —— 但团队已经不往前走了。

这类故障任何"超时/崩溃"式的监控都抓不到，因为**没有任何东西超时**。

解决思路很直接：`await` 的时候，把"谁在等谁"写进共享状态。
于是等待关系变成了一张**图**，两张就能读出来：

- **不可达等待**：我等的那个 agent 已经写了「任务完成」→ 这个答案永远不会来
- **互相等待**：存在 A→B 且 B→A 的边 → 真死锁，谁都不会先答

实现上有两条不变量，都是踩出来的：

1. **只采信"还在等**且**静默 ≤ `stale_after`"的标记。**
   否则一个被 `kill -9` 掉的 `await` 会永久留着一个假等待边，看板长期显示"它在等"。
2. **险情消失后必须清掉 key。** 有一条断言专门盯这个：
   环被打破之后不能再报同一个险情（否则修好了还在报，人会开始忽略告警）。

## 四、刻意不做：事件流替代轮询

**这是被问得最多的一个建议，也是量过才拒绝的。**

原计划就是用 inotify / kqueue / ReadDirectoryChangesW 替代 2s 轮询。先量开销，
结果发现**该修的不是轮询间隔，而是扫描本身**：

| | 修之前 | 修之后 |
|---|---|---|
| `scan_board`（2000 行看板） | 34.3 ms | **11.4 ms** |
| 单个 `await` 占单核 | — | **2.3%** |
| 6 个并发等待者 | — | **24%**（线性，零锁冲突） |

热点是 `board_entries` 里**对每一行调用一次 `datetime.strptime`**，占单轮 97%。
改成"日期段算一次本地 0 点基准 + 整数加法"后快了 3× —— 而且受益的不只是 `await`，
`post` / `check` / `brief` / `watch` / `serve` 全都要扫看板。

反观事件流：三套互不兼容的 API，Windows 上还会退化，而这个项目的卖点正是
**零依赖、纯标准库、跨平台**。拿一个确定的移植性风险去换一个"可测量的不重要"
（一次模型往返 30–60s，轮询占其中 <7%），不划算。

> 如果你有实测数据表明在某类场景下轮询真的成为瓶颈，欢迎来推翻这个决定。
> 请在 issue 里带上：看板行数、并发等待者数量、`interval` 设置、以及 `time` 实测。

## 五、刻意不做：调度

没有任务分配、没有优先级、没有重试编排。**这是有意的边界。**

编排层（谁做什么、做失败了重试几次）和可观测层（现在到底发生了什么、谁卡住了）
是两件事，混在一起会让两边都变糟：编排逻辑一旦进了看板，看板就不再是"事实的记录"，
而变成"意图的记录"，于是你没法再从它判断真实状态。

这个项目的定位是：**让状态和意图可见，让"等"可阻塞、可超时、可上报。** 就这些。

# 踩坑记录

## 踩坑记录（一）：用法错误借用了业务码

**症状**：`await --agent a1 --id 99`（编号不存在）输出 `✗ 没有编号 #99 的提问`，
但**退出码是 `1`**。而 `1` 在这套协议里的含义是「超时 / 对方没回」。

**后果**：调用方（脚本、CI、agent 驱动层）看到 `1` 会得出"对方不配合"这个结论，
然后**基于这个错事实继续往下做**。而真实原因是「我把编号写错了」。

**根因**：Python 里 `sys.exit("字符串")` 的默认退出码是 **1**。
引擎里所有前置条件错误都这么写，一共 **17 处**。源码里看不到数字，谁也不会注意到。

**更难看的部分**：回归套件里 **13 条断言原本写的就是「期望 1」** ——
等于把这个 bug 当成规格焊死了。也就是说，**测试是绿的**，
而且它还会阻止别人修（改对了反而 test fail）。

**修法**：

1. 退出码常量集中到引擎顶部 `EXIT_*`，并写明"为什么 `1` 不能被借用"——
   否则下一个人还会借。
2. 统一出口 `die(msg, code=EXIT_USAGE)`，17 处全部替换。用法错误一律 `2`。
3. 内部异常单独走 `70`（sysexits `EX_SOFTWARE`）—— 工具自己坏了是另一回事，
   绝不能 `return 1`。
4. 驱动层把 `rc==2` / `rc==70` 翻译成人话，否则模型只看到原始 stderr，照样会误读。

**三层护栏**（组 `[29]`）：

| 层 | 内容 | 为什么必须有 |
|---|---|---|
| 语义断言 | `usage()` 不仅要求 `== 2`，还把"退成 1"单独报成失败 | 只比数字会丢掉"为什么是 2"这层信息 |
| 常量表 + 静态护栏 | 锁住 `0/1/2/3/4/70`；`grep` 禁止语句位置的 `sys.exit("字符串")` 复现 | 光靠人记不住 |
| **反向断言** | 确认真超时**仍然**返回 `1` | 没有这层，一个"把所有码都改成 2"的错误修复也能让测试全绿 |

**顺带一个教训**：静态护栏的正则**必须限定"语句位置"**（行首缩进 / `;` `:` `(` `[` `{` 之后）。
第一版没限定，结果被**我自己在文档注释里引述这个坑**的文字命中了 ——
护栏写得太宽，会逼得后来人不敢在文档里记录历史，等于把知识从文档里挤出去。

## 踩坑记录（二）：内部崩溃伪装成业务结论

一次改动 `await` 之后残留了一个变量名，导致每次 `await` 都抛 `NameError`。
进程以 **1** 退出 —— 于是**所有调用方都得出"对方没回"这个完全错误的结论**。

症状很有意思：看起来像"功能失效"（险情全没了 + `await` 全超时），
实际是引擎崩了。

这就是引入退出码 `70` 的直接原因。**铁律：业务码只能由业务逻辑产生。**

## 踩坑记录（三）：`check` 检出险情却退 0

等待图做出来之后，`[互相等待]` 能被检出、能写进告警台账 ——
但 `check` 的退出码仍然只看"有没有卡死"，所以这种真死锁下 `check` 退 **0**。

后果：脚本里写 `check || 告警` **会把这类故障整个漏掉** ——
而它偏偏是这套机制最想抓的那类（心跳全绿、没有任何东西超时）。

现在"有卡死**或**有险情"都退 `1`，并补了反向断言：险情消失后必须回到 `0`
（否则"退 1"会变成永久噪声，人就学会忽略它了）。

## 踩坑记录（四）：「合法的陷阱」`--id 0`

`--id 0` 曾经是"等任何新动态"的合法写法。问题是：一旦编号在传递中丢了
（`None`、空串、格式错误），驱动层会把它归一化成 `0` ——
于是**"我丢了编号"变成了"我要等任何动静"，并且返回成功**。

这是最阴险的一类 bug：**它不报错，只是静默地做了另一件事。**

现在 `--id 0` 在 CLI 和驱动层都被硬拒（退出码 `2`）。想表达"等任何新动态"
就**不写 `--id`** —— 语义从"一个特殊的数字"变成"一个不存在的参数"，没法再被误归一化。

## 踩坑记录（五）：`--stale-after` 的默认值会误伤真模型

默认 45s（= 3 个心跳周期）是给"每一步都很快"的 agent 设的。
但**一次正常的模型往返实测 56s** —— 也就是说 agent 正在好好思考，
却被判成「疑似卡死」。

现在文档里明确建议：**真 LLM agent 场景用 `--stale-after 90`。**
这类"阈值型"参数的默认值必须对齐最慢的合法路径，而不是最快的。

## 踩坑记录（六）：stdout 缓冲

后台跑 `watch` / `serve` 是常态。stdout 一旦进管道或文件，Python 默认全缓冲 ——
于是出现"看门狗在跑、视图在跑，但一个字都看不到"。实测 `watch` 跑了 4 分钟、
输出文件 **0 行**。

修法是在 `main()` 入口统一 `sys.stdout.reconfigure(line_buffering=True)`，
而不是在每个命令里各打一次补丁。测试组 `[19]` 专门盯这个。

## 踩坑记录（七）：语言里"换行"不能进看板

看板是"一行一条"。`post` 的文本里换行会被压成空格 —— 这是**故意的**，
因为看板的可反解性依赖行文法。如果你需要多行内容，写多几条心跳。

## 附：几条通用教训

1. **静默的错最贵。** 这个项目里所有的坑都不崩、不报错，只是让调用方相信一个错的事实。
   做 agent 基础设施，优先级最高的事情是"让失败可见"，而不是"加功能"。
2. **改语义必须同步改断言。** 留着的旧断言会变成假绿，而且会阻止正确的修复。
   看到测试变红时，先问"它原来期望的到底对不对"，**不要**机械地改期望值。
3. **护栏要精确到不会误伤文档。** 否则你会亲手把知识从文档里挤走。
4. **优化前先量，量完可能发现优化错了地方。** 见「四」。
5. **阈值型默认值对齐最慢的合法路径。** 见踩坑（五）。
