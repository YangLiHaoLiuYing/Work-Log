work-log多 agent 协作的心跳看板

多个 agent 一起干活时，最贵的故障不是「崩了」，而是没人崩、但整个团队已经不动了。 work-log 让每个 agent 每 15 秒写一条心跳，用一个看门狗盯着， 把谁静默了、谁和谁互相等死了、谁在无限客套直接摆到页面上。

本页所有数据均取自仓库内 examples/demo-output.txt —— 那是这套 CLI 的真实输出，未经美化。

01

谁静默了，第一眼就看见 看门狗

三个 agent 都在写心跳，agent3 写到一半不吭声了。 看门狗扫描时发现它静默 4.5 秒、超过阈值 3 秒，且没写「任务完成」—— 于是标红告警。只有 agent3 变红，另外两个静默 0.3 秒属于正常，不会被误报。

02

心跳全绿，也可能是死的 等待图 · 本工具独有

场景：agent1 和 agent2 互相问了对方一个问题，然后两边都阻塞等对方回答。 因为 await 期间会持续续心跳，所以双方心跳都很勤—— 看门狗看它们是「最健康的两个人」，但整个团队其实已经死了。 work-log 会去读提问关系图，把这条环指出来。

只看心跳的看门狗看到：
● agent1 心跳中 ● agent2 心跳中 → 一切正常
work-log 读到提问关系图后：
▲ 互相等待 agent1 ⇄ agent2 → 真死锁
互相等待 <agent1> 与 <agent2> 正互相等对方回应
各卡在自己的 await 里 —— 谁都不会先答，这是一条真死锁。 需要有一方先 brief 看到「待你回应 #N」并 reply，或由在线 agent 介入。

这一步就是 work-log 相对其它多 agent 方案唯一独有的能力： 检出「心跳全绿的死锁」。所以 check 在这里也必须是非零（1）， 否则这类故障在脚本里会被整个漏掉。

03

两个 agent 客套起来停不下来 通信熔断

同一对 agent 连续交替来回、期间没有任何第三方或用户消息插入 —— 这几乎肯定是「互相确认」而不是推进。到 6 轮开始提醒，到 12 轮直接拒绝写入， 把预算花在推进上，而不是「好的」「收到」「那就这样」的无限循环。

蓝色 = agent1 发言，青色 = agent2 发言 —— 全程没有第三方插话
✗ 通信熔断：<agent1> 与 <agent2> 已经连续来回 12 轮， 期间没有任何第三方或用户消息插入 —— 这几乎肯定是「互相确认」而不是推进，已经替你停下。
　收敛：post --agent agent1 --tag 决定 --text "结论是什么、接下来谁做什么"
　确实还要深挖：在刚才那条命令后加 --force
退出码 = 4（4 = 被机制叫停，不是参数错）

--force 可以放行，但熔断的用意是先逼出一句结论： 谁做什么、下一步是什么。

04

一次等多人，谁先答都能往下走 多路 await

默认是「全部都要」（--id 1,2）；加 --any 变成「任一即可」。 后者拿到第一条回应就返回，不会为了等齐所有人干耗。

--any 的实际语义是「任一回应即达成」，拿到一条就返回。 配合定向提问 ask / reply，就能把「等人」这件事变成可判断的状态。

跑起来看看

# 0) 在仓库根目录下（克隆下来就能跑，不需要装任何依赖）
WL="scripts/work_log.py"

# 1) 初始化一块看板（默认落在 ~/Desktop/work-log/<当前目录名>/）
python3 $WL init --task "给项目加个语音开关"

# 2) 每个 agent 每 15s 写一条心跳
python3 $WL post --agent agent1 --text "收到，正在改 backend/tts.py" --tag 收到

# 3) 另开一个终端：起看门狗 + 浏览器实时视图
python3 $WL serve            # → http://localhost:8787
