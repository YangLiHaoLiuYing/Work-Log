# 验收：它凭什么算"能用"

这份文档只回答一个问题：**凭什么相信这个东西是有效的，而不是一堆能跑通的代码？**

结论先说：

| 项目 | 结果 |
|---|---|
| 回归断言 | **32 组 290 条，0 失败**，Python **3.9.6** 与 **3.13.12** 上各自全绿 |
| 真机验收 | 真实模型驱动 2 个 agent 走完整协议 **3 轮**（第 1 轮因驱动层 bug 作废，第 2/3 轮有效） |
| 看门狗误报 | 3 轮全程 **0** 条 |
| 性能 | 2000 行看板下单个 `await` 占单核 **2.3%**；6 个并发等待者 **24%**（线性，零锁冲突） |
| 退出码契约 | 18 种坏调用逐条扫描，全部退 `2`，**没有一种借用业务码 `1`** |

## 1. 回归断言（你自己可以复现）

```bash
bash scripts/selftest.sh          # 用你 PATH 里的 python3
PYTHON=/usr/bin/python3 bash scripts/selftest.sh     # 指定解释器
```

约 3 分钟。只在 `mktemp -d` 出来的临时目录里折腾，**不碰你的项目文件**，
结束自动清理。退出码 `0` = 全通过。

实际输出（节选）：

```text
[29] 退出码契约（用法错误 → 2，且绝不许退成业务码 1）
  [ok] 退出码常量 = 0/1/2/3/4/70
  [ok] 前置条件错误统一走 die()
  [ok] 源码里不再有语句位置的字符串型 sys.exit（会退 1）
  [ok] 「空心跳文本」→ 2
  ...
  [ok] 「--id 0」→ 2
  [ok] 「缺必填参数」→ 2
  [ok] 对端在线但不答，超时仍是 1
  [ok] 驱动层翻译了 rc=2（用法错误）
  [ok] 驱动层翻译了 rc=70（工具坏了）
----------------------------------------
```

### 覆盖了什么

不是"每个函数各点一下"，而是**围绕每个失败模式覆盖到它的误报边界**：

| 组 | 覆盖 |
|---|---|
| 1–9 | 初始化 / 心跳格式 / 参数校验 / 待启动保护 / **20 进程并发写不丢行** / 卡死判定与冷却 / 恢复自动闭环 / 「任务完成」退出监督 / `hold` 长任务挂起 |
| 10–11c | 资源锁 / 用户喊话与认领 / 探针 `brief` 的增量语义 / 定向问答全链路（问→答→等→回执） |
| 12–17 | 手写看板反解 / 脏输入健壮性 / 机器可读输出 / 跨天分节与状态裁剪 / 看门狗 / 未初始化边界 |
| 18–22 | 依赖检查（**必须零第三方**）/ 后台实时输出不被缓冲憋住 / `serve` 真起服务真发请求 / 默认目录按项目隔离 / 串项目检测 |
| 23–24 | 静默挂起 `hold --quiet` / 驱动层参数解析（套壳、缺字段、三种 `await` 出口的翻译） |
| 25 | **协作险情**：不可达等待被认出且不误报卡死、`--json` 暴露 `hazards[]`、告警落盘 + 冷却不刷屏、过期标记不采信、互相等待认成真死锁且不误判成不可达、环破后险情消失、**有险情时 `check` 必须退 `1`**、**险情消失后必须回到 `0`** |
| 26 | **通信熔断**：乒乓 6 轮警告 / 12 轮硬拦退 `4` / `--force` 放行 / 非交替批量对话不误判；心跳预算超线退 `4` 且**不刷新** `last_seen` |
| 27 | **多路等待**：全部到达 / `--any` 首个到达 / 混合（已答 + 已收工）退 `3` 但仍打印已拿到的答复 / 等不存在的编号与等别人的编号都提前报错 / `--id 0` 与 `--any` 缺编号都被拒 |
| 28 | **看板解析防退化**：3004 行看板里 `strptime` 调用次数必须 ≤ 8（实测 0） |
| 29 | **退出码契约**：常量表 / `die()` 存在 / 静态护栏 / 18 种坏调用 / 反向确认真超时仍返 `1` / 驱动层翻译 `2` 与 `70` |

### 为什么有些断言"不数数字，数语义"

两个例子，都是为了**让断言在机器变了之后依然拦得住回归**：

- **第 28 组数的是 `strptime` 调用次数，不是秒数。** 数秒会随机器负载飘，
  同一个回归在不同机器上时松时紧；数调用次数是语义不变量 ——
  「不许把通用日期解析塞回逐行循环」，与快慢无关。
- **第 29 组把「退成 1」单独报成失败。** 而不是简单断言 `== 2`：
  将来有人把码改成别的数字，报告会告诉你"数字变了"，而不是丢掉"用法错误不许伪装成业务结论"这层信息。

## 2. 真机验收（这部分你复现不了，只能看证据）

回归套件能证明"代码按我写的规则跑"，**证明不了「真模型会照这个协议做事」**。
所以另做了一轮：用真实模型（OpenAI 兼容端点）当 agent，走完整协议。

### 方法

两个 agent，各自接到一个**互相冲突**的用户要求（各自要改同一个接口的不同方面）。
它们必须自己发现冲突、互相提问、协商出一个折中，然后各自写下决定。

### 结果

| 验收标准 | 结果 | 依据 |
|---|---|---|
| 双方各有「提问→X #N」与「回应#N」，编号能对上 | ✅ | `#1`、`#2` 双向交换状态均为 `closed` |
| 决定里能看出**读了对方的原话** | ✅ | agent2 的 `[决定]` 开头即「基于 agent1 回答：典型 20~100 字、长段落 300~500 字、字段 text」 |
| 面对与已定结论冲突的用户要求，不沉默也不嘴上答应 | ✅ | 走「阻塞 + 协商 + 显式折中」，并在决定里写明折中理由 |
| `await` 超时会如实上报，不编造对方回答 | ✅ | 超时分支输出「对方还没回答，你什么都没收到」 |
| 看门狗不误报 | ✅ | 3 轮全程 **0** 条 |

### 这一轮真正花时间的地方

不是「模型行不行」，而是**驱动层自己的 4 个 bug**，而且**每一个都伪装成「模型不听话」**：

1. 工具参数的对象壳 / 字符串壳没剥干净 → 模型看起来在乱传参数
2. `await` 缺 id 时静默退化成 `--id 0`（"等任何动静"）→ 看起来像"模型在瞎等"
3. `subprocess` 超时预算算错 → 看起来像"模型反应慢"
4. 出口文案把 `3`（对方已收工）说成超时 → 看起来像"模型不认账"

**教训：判定一个协作机制之前，必须先把驱动层排干净。** 否则你测的是自己的 bug。
（顺带：第 1 轮因此作废，只剩第 2/3 轮有效。）

## 3. 性能：先量，再决定优化什么

原计划要做"事件流替代 2s 轮询"。**先把开销量出来**，结果发现该修的不是轮询间隔：

| 环节（2000 行看板 / 75KB state） | 修之前 | 修之后 |
|---|---|---|
| `scan_board`（读 + 逐行解析） | 34.3 ms | **11.4 ms** |
| `load_state` / `save_state` | 3.2 ms | 3.2 ms |
| 单轮合计 | ~37 ms | **~14 ms** |

热点是 `board_entries` 里**每行一次通用日期解析**（`datetime.strptime`），占单轮 **97%**。
改成「日期段算一次本地 0 点基准 + 整数加法」后降到 11.4ms（**3×**）。

端到端（修之后，2000 行看板）：

```text
默认 interval 2s，等 20s        →  0.47s CPU / 20.5s = 单核 2.3%
interval 1s（激进），等 10s     →  0.41s CPU / 10.5s = 单核 3.9%
6 个并发等待者，interval 1s，10s →  合计 2.54s CPU / ~10.6s = 单核 24%（每人 4%，线性，零锁错误）
```

**结论：不做事件驱动。** 一次模型往返 30–60s，轮询占其中 <7%。
拿三套互不兼容的 API（inotify / kqueue / ReadDirectoryChangesW，Windows 上还会退化）
去换一个"可测量的不重要"，不划算 —— 而这个项目的卖点正是零依赖、纯标准库、跨平台。

理由和数字写在 [`DESIGN.md`](DESIGN.md)，欢迎带实测数据来推翻。

## 4. 已知盲区（没测出来的部分，如实列出）

- **「还在动但方向错了」测不出。** agent 每 15s 老实写心跳，但一直在改错文件 / 无限重试。
  任何基于心跳的机制都是盲区，包括这个。
- **「等外部条件」测不出。** CI 队列、模型下载、端口占用 —— 等待对象不是 agent，等待图不建模。
- **`hold` 之后开始摆烂测不出。** `hold` 的作用是"别判我卡死"，所以它可以被滥用成免死金牌。
  这是设计取舍（否则长构建必然误报），不是 bug。
- **Windows 上退化为无锁。** 没有 `fcntl` 时并发写靠不住，几个本机进程够用，分布式不要用。
- **真机验收只有 3 轮、2 个 agent。** 样本小。它证明的是"协议能被真模型走通"，
  不是"在所有模型上都稳"。

## 6. 测试自身的已知局限（如实说）

- **有过一次偶发失败，根因已查明并修复。** 2026-09-19 的一次全量运行里，第 11 组的
  `brief 报告别人的锁` 失败了一次（248 通过 / 1 失败）；随后多次全量运行未能复现。
  最终用 **6 路并行压力**复现（6/6），定位到**两个测试自身的封闭性缺陷**（不是引擎 bug）：
  1. 该组里的 `损坏 state.json 不崩` check 断言漏了 `--stale-after 999`，用了默认 45s
     阈值 —— 慢/高负载运行里，看板上已收工 agent 的最后心跳超过 45s，被标"疑似卡死"，
     `check` 返回 1，断言误判失败（全套件唯一漏掉 999 的一处）。
  2. 第 21 组隔离测试用了全局固定路径 `/tmp/wl_iso_a|b`：两个并行套件实例互相 `rmdir`
     掉对方 `cd` 的目标，`Path.cwd()` 抛 `FileNotFoundError`。
- **已做的修复**：(1) 补上 `--stale-after 999`；(2) 隔离测试路径改到套件自己的 `$TMP` 下；
  (3) "不同目录"断言补了反向检查（两个路径必须都非空，否则两边都空时"不同"会假绿）。
  断言数 249 → 250。
- **修复后的验证**：6 路并行压力 **6/6 全绿**（修复前同条件 6/6 失败）；
  Python 3.9.6 与 3.13.12 各自全量 **250/0**。
- **仍然成立的设计取舍**：本套件里若干断言依赖真实子进程与时序
  （并发写、后台 `watch`、`await` 超时），在负载很高的机器上仍有抖动空间。
  如果你在 CI 里遇到偶发红，**先重跑一次确认是否复现，再带失败信息提 issue** ——
  复现不了的失败，比复现得上的失败更值得报告。
