# 身份：名字怎么固定 + 同名多实例怎么认

> 本文件是 `SKILL.md` 的延伸阅读 —— **正文只留判据与触发条件，细节都在这里**。
> 什么时候读它：一台机器上同时开着两个同名工具（两个 `opencode`）、要判断某个 agent 认不认得出、或要理解「像宿主」的完整判据。

---

## 名字怎么固定（三个会话别撞进同一个身份）

为什么值得单开一节：**两个会话用同一个名字，板上完全看不出来**。`_get_agent` 按名字取的是
*同一个 dict* —— 心跳、`entries`、未读游标、`awaiting` 全混在一起，看板上像"一个人干得挺欢"。
而这个工具整套判断（谁卡死、谁在等谁）都建立在那份状态上。

固定身份是**三件互补**的事，缺一件就会在某个场景下漏：

| 想要的效果 | 怎么做 | 靠什么 |
|---|---|---|
| 这个**会话**钉死一个名字 | 让驱动层 / launcher 设 `export WORK_LOG_AGENT=a1` | 环境变量跟着进程走，换目录也认 |
| 这个**目录**默认是谁 | `work_log.py --dir D identity set --agent a1` 登记一次 | 板上 `identities.json`（跟着板走，换会话还在） |
| 别的地方不许抢这个名字 | 什么都不用做 —— 上面的 `set` 会自动拒绝 | 拒绝时会把**占用者目录**打出来 |

三条硬规矩：

1. **别把某个 agent 的名字写进共享文件。** 仓库里的 `AGENTS.md` / `CLAUDE.md` 会被
   **任何在该目录启动的 agent** 读到 —— 写死 `--agent a1` 等于给所有会话发了同一个身份。
   共享文件里只写「义务 + 看板坐标 + 名字从哪来」，名字本身交给环境变量或登记表。
2. **同一个 cwd 开两个会话，必须显式区分。** 按目录只能认到一个人；两个人都落在那个目录时
   `resolve_agent` 会**退 2 拒绝猜**（那里登记了不止一个名字时同理）。
3. **换了机器的同一角色，重新登记一次**（`identity set`）。环境变量不会跟着你换电脑，
   板上的登记表会 —— 但只有你把它登记对了才有用。

### 同一个工具开着**多个实例**怎么办（两个 opencode / 两个 claude）

这是上一节的近亲，但**旧机制挡不住**：上表那条"别的地方不许抢这个名字"靠的是 **cwd 冲突**，
而同一台机器上的两个 `opencode` 往往**就在同一个仓库里**（cwd 完全相同）⇒ 冲突检测看不见它们。

**会静默坏在哪**（不是"名字不好看"，是判断失效）：

| 被合并的东西 | 后果 |
|---|---|
| `last_seen` | 一个实例死了，另一个照样刷新 ⇒ **看门狗永远测不到它** |
| `user_cursor`（用户喊话未读游标） | 一个实例 `read-user` 推进了游标 ⇒ **另一个永远看不到用户的喊话**（消息静默丢失） |
| `entries` / 心跳预算 | 两个实例共用一个 60 条/分的额度，互相把对方顶到**熔断退 4** |
| `expected_silence_until`（`hold` 挂起窗口） | 同名实例都可 `release`/`hold` 改写它 ⇒ 你声明了长任务、却被**别人**解掉或改短，随后照样判你卡死告警（post 已不清窗口，但同名下挂起状态仍不可信；2026-09-28 实测：hold 到 21:24:37，21:22:45 就被报"已静默 1m32s"） |
| `awaiting` / `ask` 归属 | 答复可能被"另一个实例"先 `await` 走 |

**处理办法（推荐，且只有这一种是可靠的）：一实例一名字，用环境变量在启动器里钉死。**
不要用 `identity set` 指望它区分 —— 它按目录认，同目录第二个名字会被**退 2 拒绝**（那是对的）。

```bash
# 实例 1 的终端 / 启动器
export WORK_LOG_AGENT=opencode-eval
# 实例 2 的终端 / 启动器
export WORK_LOG_AGENT=opencode-ui
```

命名建议用**角色**而不是编号（`opencode-eval` / `opencode-tail` 比 `opencode-1` / `opencode-2` 好读：
板上「谁在干什么」一眼能看出来，接管时也不用先查编号）。

**做不到及时改名也没关系 —— 工具会替你把这件事说出来。** 从 2026-09-28 起：

- `post` 认出「这个名字下又来**第二个实例**」时，当场打印 `⚠ 同名多实例：…`
  并往板上写一条 `<watchdog> [协作]` 留痕（只写一次，不刷屏）。
- `status` 那一行会标 `⚠同名 2 实例（共用身份，见 doctor ⑦）`。
- `doctor ⑦` 列出每个名字下的全部实例，并给出改法提示（有病退 1）。

实例标识怎么来的：优先 `$WORK_LOG_INSTANCE`（最准，多实例场景建议显式设）；
否则沿**父链**往上找第一个像 agent 宿主的进程，用 `pid@启动时刻` 当标识。

**「像宿主」的判据很严，这是故意的**（2026-09-28 实测修正过三次，坑都很隐蔽）：

- 只看 **argv 里的可执行名**；对"跑脚本的进程"会去 **argv[1]** 找真身
  （`node …/claude-code/cli.js`、以及 macOS 上 shebang 脚本被显示成
  `/bin/sh /路径/opencode …` 这两种），**绝不对整条命令行做子串匹配** ——
  实测有程序把**整块环境变量 JSON** 当参数传，里面就有 `CLAUDE_PLUGIN_ROOT`；
  一句 `"claude" in cmd` 会把**宿主自己**认成 claude。
- **`-c` / `-e` 这类开关不算路径，一律跳过** —— agent 起我们往往是
  `bash -c "… post --text 'opencode 卡住了' …"`，argv 里就带着关键词；
  认它等于**每次 post 都换一个锚点**（那种 shell 是一次性的、pid 每次都变）。
- **`.app` 包里的进程一律不算宿主**（结构性判据，看路径里有没有
  `.app/Contents/MacOS/`）。那是"一个进程承载多个会话"的形态 ——
  拿它当锚点会把好几个会话算成**同一个**实例，等于**看起来正常，其实在撒谎**。
  桌面 App（含 WorkBuddy 自己）都走这条。
- **命中名字了也不够：宿主要活够 20 秒才敢用**。刚起的短命进程锚上去，下次就认不出
  （锚点乱跳 = 假的多实例告警）；测不出年龄时不拒绝。
- 启动时刻强制以 **`LC_ALL=C`** 取（`lstart` 的月份是按 locale 渲染的字符串，
  用户 `LANG` 一变就会把**同一个进程**算成两个实例）。
- 锚点还会**查死活**：宿主进程已经不在（或那个 pid 已被系统复用给别人）⇒
  那不是"另一个并发实例"，是**同一个会话换了宿主** ⇒ 静默替换，不告警。
  （没这条的话，用 `someagent run "…"` 这种"一次一个进程"的用法会**刷满假告警**。）

**认不出就返回空串、跳过判断 —— 不猜。** 宁可"报不出来"，也不能"报一个乱跳的"：
乱跳的标识会把**同一个会话**报成多个实例，比不报还糟。

### 同名**多线**：一个名字被两个不相干的目录用过（2026-09-28 新增判据）

上一节说清了「实例探测对一进程多会话的形态给不出答案」。那种形态恰恰是最常见的
（本机实测：两个 WorkBuddy 会话并发，都叫 `workbuddy`，`instances` 为 0、板上零痕迹），
于是合并照样发生却没人看见。补上的判据是 **cwd**：

- `post` 时记下这个名字第一次出现的目录（`agent.cwd`）；
- 之后再从**不互为子目录**的另一个目录用同名发帖 ⇒ 当场警告发帖的人 +
  板上留一条（同一个目录只留一次，`agent.cwd_warned` 记住喊过谁）+
  `status` 标 `⚠ 同名多线` + `doctor ⑦a` 列清两个目录；
- **嵌套目录不算**（`repo/` 与 `repo/backend/` 是同一个人的里外，不是两条线）。

为什么是 cwd 而不是别的：它是工具本来就握着、且**不需要猜**的证据 ——
与这套工具「判据不许猜」的纪律一致。它补不上「两个 opencode 在同一目录」那一种，
那种只能靠显式改名（上一节）。

复位：`agent.cwd` / `cwd_conflict` / `cwd_warned` 都在 `state.json` 里，
给两条线各自登记名字之后，旧的冲突标记会随那一行留在板上（它是历史证据，不自动清）。

### cwd 判据对**常驻进程**不成立（2026-09-29 实测）

上一节的判据是 cwd。它有一条前提没写：**发帖进程的工作目录得落在项目里**。
常驻驱动进程不满足 —— `launchd` / `launchctl` / `systemd` / `nohup` 起的后台进程，
cwd 是它自己的脚本目录（实测：`.workbuddy/..`），既不是项目根也不是用户手选的目录。
后果是两种错法同时可能：目录不同 ⇒ 误报「同名多线」；目录恰好相同 ⇒ 该报的合并不报。

本机实测的现场（2026-09-29 21:46）：`opencode-bot` 这个名字同时被
一个交互会话（pid 34824）和 `launchd` 监听器每次 spawn 的 bot（pid 34494）使用。
`doctor ⑦b` 只看父进程链，看不出「两个不同进程共用一个身份」；
`cwd` 也判不了（一个是终端会话、一个是后台进程）。
`last_seen` / 用户喊话游标 / 心跳预算全部合并 ⇒ 同一条 `user.md` 消息被两边各当未读、
各自 `ack-user`，板上只留两条回执、看不出重；且任一方活着就能替对方续命，看门狗测不到另一个死了。

**所以常驻驱动线必须自己起一个独立名字**（`opencode-bot` 给监听器、TUI 那条另起
`opencode-bot-tui`），不要指望机制发现 —— 这一条**没有自动检测**，靠命名纪律兜。
`doctor` 补的方向是「同名下有多个 pid 且不在同一进程树」，本版未实现。

#### 改名**不迁移**实例归属（2026-09-29 22:05 实测，会造成 doctor 误报）

`identity set` 改的是 `identities.json` 的「名字 → cwd 登记」和之后 `post` 的署名；
`state.json` 里 `instances` 的**历史 pid 记录仍挂在旧名字下**，不随改名迁移。
所以一条线改完名以后，`doctor ⑦b` 会**继续**报「<旧名> 下有 2 个实例」——
而其中一个 pid 正是它自己。实测：`opencode-bot-tui` 21:48 从 `opencode-bot` 改名后，
`opencode-bot` 名下仍是 `21311@21:26:28`（它自己的宿主）与 `44264@22:01:32`
（listener 那条线新 spawn 的），两边照旧共用 `last_seen` / 喊话游标 / 心跳预算。

判读纪律：**看到「同名多实例」先问「这一条是不是改过名的残留」**，
别直接当成「有两个活实例互相替对方续命」——后者更严重但不是事实。
核对方法：`identity list` 看新名字是否已登记，再看 `doctor ⑦b` 列的两个 pid 的进程是否还活着。
真正要修的是让改名**迁移或作废**旧名下的实例归属；本版没做，所以
「撞名就改名」这个处方在常驻场景下**只解决一半**：署名与游标分开了，pid 归属还重叠。

### 「注入返回 200」不等于「送达」（2026-09-29 22:06 实测）

判断「外部能不能唤醒某个 agent」时，最容易犯的错是**拿一个便宜的验证冒充真验证**。

实测现场：`opencode serve` 起 headless server 后有完整 HTTP API（openapi 在 `/doc`），
其中 `POST /tui/append-prompt?directory=<dir>`（body `{"text":...}`）与
`POST /tui/submit-prompt?directory=<dir>` 看起来正是「往 TUI 塞消息」的入口。
**两次实打都返回 200 / true** —— 但随后查该 TUI 会话的 120 条 message，
**注入的内容一条都不在里面**。端点存在 ≠ 对这条 TUI 送达。

`directory` 参数并不路由到某个独立的 TUI：只有 **attach 了同一台 server** 的 TUI 才收得到。
所以准确表述是「**入口在，未 attach 就不通**」——
既不是「没有入口」（那是查得不够），也不是「有入口就可用」（那是验得不够便宜）。

**判据**：声称「我能唤醒 X」之前，必须去 **X 自己的会话记录里查到那条注入内容**。
只有 HTTP 200、`lsof` 看到端口、端点列在 openapi 里，都不算。

同一类错误今天出现过两个版本，性质相同：
一边是「拿 `bash -n` 给没发生的改动背书」，一边是「拿 200 给没送达的注入背书」。
**便宜的验证通过 ≠ 事情成立。**

可行的替代形态（今天端到端跑通的）：不追求唤醒 TUI，改成
**把「有人 ask 我」变成 spawn 事件** —— 轮询 `state.json` 里 `status=open`
且 `to=<本线>` 的提问，发现即 `spawn opencode run` 去 `brief` + `reply`
（`scripts/ask_listener.sh`）。它只把人叫起来、不代答，对任何没有宿主唤醒机制的
TUI 都成立；缺点是每次应答是一个独立进程，不共享原会话上下文。

### 怎么知道「我用的那个 agent 认不认得出」

```bash
work_log.py doctor --explain      # ⑦b 会把父链逐层判定打出来
```

它会列出每一层为什么被跳过（不像宿主 / App 包 / 太年轻），并给出结论。认不出时给两条补救：

| 情况 | 补救 |
|---|---|
| 你的工具名不在内置名单里 | `export WORK_LOG_HOST_HINTS=<你的工具名>[,<另一个>]` —— **不用改代码** |
| 宿主是"一进程多会话"（桌面 App、tmux…） | 分不出会话，必须显式钉：`export WORK_LOG_INSTANCE=<名字>-<实例名>` |

> **名单天生会落后**：新 agent 工具层出不穷，所以别指望内置名单齐全 ——
> `doctor --explain` 会把你机器上的真实父链和名单一起打给你看，缺什么一望便知。

**本机实测过的形态**（2026-09-28，`ps` + `file` 逐个核过）：

| 工具 | 跑起来时 `ps` 里长什么样 | 认得出吗 |
|---|---|---|
| `opencode` | `opencode`（Mach-O，进程名就是它） | ✅ |
| `claude`（Claude Code） | `…/.local/bin/claude`（Mach-O） | ✅ |
| `kimi`（Kimi Code） | `…/.kimi-code/bin/kimi`（Mach-O） | ✅ |
| `hermes` / `hermes-agent` / `hermes-acp` | `~/.local/bin/hermes` 是 **4 行包装、`exec` 掉自己** ⇒ 真身是 `…/venv/bin/python …/hermes-agent/hermes` —— 靠「解释器 + 脚本」那条规则认出 | ✅ |
| **Hermes 桌面版** | `Hermes.app/Contents/MacOS/Hermes`（Electron，一个 App 进程承载所有会话） | ❌ **按设计跳过** —— 分不出会话，硬认会把几个会话算成同一个 |

> 结论：**CLI 形态基本都认得出，桌面 App 形态一律不认**（不是漏了，是那种形态本来就
> 分不出会话）。用桌面 App 的 agent 想区分会话，只能显式
> `export WORK_LOG_INSTANCE=<这个名字>-<实例名>`。

实例标识最长保留 7 天（换过锚点口径后，幽灵实例不会永远挂在看板上）。
不想被探测就 `export WORK_LOG_NO_INSTANCE=1`。

## 存活形态声明：名字不光回答"我是谁"，还回答"我的活法"

登记表里除了「名字 ← 目录」，还可以声明**这条线怎么活着**。这不是备注，是**判据的输入**：

| 声明 | 命令 | 改了什么判据 |
|---|---|---|
| **spawn 即活型** | `identity set --agent X --spawn --purpose "被 <谁> 唤醒"` | 心跳轴**不再**判它卡死（它平时零心跳、被叫才起）。**必须写 `--purpose`**：这条声明的效果就是"让看门狗闭嘴"，不带理由的静音就是藏身处，代价必须付在前面 |
| **循环型** | `identity set --agent X --loop` | 「任务完成」标签对它**不生效**（它永远不收工）。见下 |
| 撤销 | `--no-spawn` / `--no-loop` | 回到默认判据 |

两个都不会让这条线**逃出监管**：它们只是换了心跳轴的判据，**办事轴照样盯着**
（一个 spawn 型 agent 被问了不答，仍然是事故）。

### 为什么“循环型”值得一个声明 —— 一个标签同时是两个开关

「任务完成」在引擎里同时是：

- 心跳轴的**豁免开关**（"别报我卡死"）；
- 办事轴的**事实声明**（"我不会再答了" ⇒ 问它的提问归成「该结案」= 不用管）。

于是一个循环进程（守护 / 监听 / 看门狗）只要把**自己的心跳**也打上这个标签，
就一次性拿到两份豁免，**而板上完全看不出来** —— 2026-09-29 真有一个这样的守护进程
（`ask-listener-guard`）这样跑了半小时：它每一轮自报心跳都写「任务完成」，
于是所有问它的提问都被判成"该结案"。而且它的动机并不是骗人 —— 是**别人告诉它
"收工要写这个 tag"**，它照抄了。教训：**别把只适用于一次性进程的规则抄给循环进程**；
同理，**豁免必须校验资格**，不校验资格的豁免迟早被当成漏洞用。

兜底（不需要任何人声明）：引擎还会看**尾部连续写了多少条完成标签** —— ≥3 条**且**相邻
两条间隔在办事轴窗口内，就**提醒**一次（`status` / `check` 里点名），但**不改判**它的
完成状态。只提醒的理由见 `references/protocol.md`：真板上试过"≥3 条就直接作废"，
当场误伤了**最主要的用法**。两条推翻规则的完整表也在那里。

`identity list` 会把这两个声明打在那一行上（"spawn 即活型" / "循环型（永不收工）"），
`status` 也会在状态行尾标出来 —— **下一个人不必再去翻文档猜「它为什么没被判卡死」**。
