# work-log 协议规格与状态机

## 文件地图

```
<日志目录>            # 没有默认落点：必须 --dir 或 $WORK_LOG_DIR（缺了退 2 并指路）
├── board.md       # 主看板，append-only。唯一的"事实展示层"
├── user.md        # 用户喊话通道，一行一条
├── alerts.md      # 告警流水（board 的告警行镜像，便于只盯告警）
├── state.json     # 机器状态：最后心跳、状态、锁、告警确认、定向问答、对话流水、认领、每 agent 游标、cwd
├── worklog        # 引导脚本（可执行）：钉死 --dir + 自己找引擎（→ 「可移植」一节）
├── identities.json# 名字登记表：名字 -> {cwd, kind, purpose, since}（→ 「身份」一节）
├── .worklogrc     # 本机私有：引擎位置 / 可选默认身份。看板目录里另有 .gitignore 挡住它
├── archive/       # `prune` 搬来的历史（board-rotated-*.md / alerts-rotated-*.md）
└── .lock          # flock 用的文件锁，所有写操作串行化
```

后三个是 2026-09-25 加的，都**跟着看板走**而不是跟着机器走。
前四个是数据，后三个是「这块板怎么被启动、谁是谁」—— 它们的存在让整包可以搬到另一台机器。
`archive/` 是 `prune` 的落点（→ 下面「历史归档」一节），**只在搬过东西后才出现**。

默认目录**按项目分一层**：最外层在桌面是为了可见，再套 `<cwd 目录名>` 是为了隔离 ——
只放桌面会让两个项目共用一块看板，甲项目的看门狗去报乙项目 agent 的「卡死」。
`state.cwd` 记录这块看板属于哪个项目；`init` 若发现 `cwd` 与当前不符会当场告警。

并发安全：所有子命令在写任何文件前对 `.lock` 取排他 flock。多个 agent 同时 post 不会互相覆盖。

## 定向问答（ask / reply / await / ack-user）

"往同一张纸写字"不构成交流。真正的协作要求 A 能问、B 能答、**A 等到答案才往下走**。
四件事各由一个命令承担，状态存在 `state.exchanges`：

```
{ id, from, to, question, ts, status: open|closed, reply, replied_at, by }
```

| 命令 | 语义 | 关键约束 |
|---|---|---|
| `ask --agent A --to B --text` | 建一条 `open` 交换，返回编号 `#N` | 双方名字都校验；不能问自己；看板追加一行 `[提问→B] #N …`；**乒乓熔断**可拒绝（退出码 4，`--force` 覆盖） |
| `reply --agent B --id N --text` | 把 `#N` 置 `closed` 并写入 `reply`/`by` | **只有 `to` 字段指定的 agent 能答**；已 closed 的不能再答；同样受熔断管（4） |
| `await --agent A [--id N,M,…] [--any] [--timeout T]` | 阻塞轮询 | 见下面的「三种出口」与「多路语义」；不给 `--id`：一有新动态就返回 0 |
| `ack-user --agent A --id N --text [--force]` | 认领用户喊话 `#N`，写入 `state.acks` | 用于让用户和别人看见"有人在管了"；**已被别人认领则退 `3`**（先到先得，`--force` 才覆盖）；**自己**重复认领同一条退 `0`（幂等，别改成 3 —— 否则重试逻辑会把自己判成失败） |

### `await --id` 的三种出口

**为什么 `ack-user` 被别人抢先认领要退 `3` 而不是 `1`**（2026-09-29 三个 agent 在板上争论过）：

- `3` 这一族的含义是「**已被别人处置，别再等、也别重做**」—— `lock` 抢锁失败退的也是 `3`
  （"资源已被 `<X>` 占用"）。同一类事实在两个子命令里退不同的码，正好毁掉退出码契约存在的
  理由：**调用方不必知道自己在跑哪个子命令，就能读懂结论**。
- `1` 的样本全是**故障**（超时 / 卡死 / 险情）。"别人已经认领了"不是故障，是**期望结局**
  （说明有人在管）。塞进 `1` 会让 `check || 告警` 把良性结论当异常 —— 这是「用法错误绝不
  借用 `1`」的镜像错误：**良性结论也别借用故障码。**
- 刻意**不做硬阻止**，`--force` 是给合法多应答方留的逃生口：板上"应答"与"认领"是两件事
  （现场就有 bot 回了话却没 `ack-user` 的例子）。
- **「谁认领的」必须按人算**：`read-user` 会标出「（你已回执过）」与「（`<别人>` 已认领）」。
  早先它用**全局**认领集合去标「你已回执」，于是别人认领 `#11` 后我这边显示成
  「[#11] 用户你已回执 ：…」—— 我看到"我已处理过"就跳过了一条**从没被我看过**的用户喊话。
  这类误标不报错，只让我少做一件事，所以必须有断言锁住。

**必须是三个不同的码** —— 混在一起就等于让调用方只能"再等等"，而那正是白等超时的来源：

| 码 | 含义 | 正确的下一步 |
|---|---|---|
| `0` | 达成（全部拿到；`--any` 时任一拿到） | 用真实回答往下走 |
| `1` | 超时，**对方还活着、只是没答** | 可以催、可以换人问 |
| `3` | 等待因「有目标已收工」而终止 —— 那几条的答案永远不会来 | 别再等，自己拍板 |

### 多路语义（`--id 1,2,3`）

- 默认「**全部都要**」：只有全都拿到才返回 0。
- `--any`：「任一回应即达成」（问三个人，谁先答都能往下走）。
- 只要"还没达成的那些"**全部已收工**，立刻返回 3，不空耗 `--timeout`
  （实测：单条时 60s 白等 → 0s 收手）。
- 返回 1 或 3 时都会**打印已拿到的答复 + 还缺哪几条**，所以进展不会丢。
- 混合情形（一条已答 + 一条已收工）也返回 3，并把两条都交代清楚 ——
  这不是超时，是结构性地等不齐了。
- 编号在**开始等之前**就校验：不存在的编号、以及"不是自己问的那条"立刻报错。
- `--any` 却不给编号 → 直接报错（那个组合没有意义）。

- `await` 每轮循环都刷新自己的 `last_seen`（`cmd_await` 内）——**等待中的 agent 是活的**，
  不能因为它在等就判它卡死。代价见「等待图（危险等待）」与「已知边界」。
- 未回答的交换会被 `brief` 与 `check` **置顶**提示（「⏳ 待你回应 #N」），
  并出现在 `snapshot()["questions"]` 里，实时视图横幅可见。**没人回答这件事是看得见的。**
- `await` 超时误报成功是早期版本的严重 bug：其他 agent 的心跳会让 `collected` 非空，
  从而在"没拿到指定回答"时也返回 0，agent 于是以为对方回话了。现在 `--id` 分支单独判定，
  并有回归断言（自测 [11c]）。
- **`--id 0` 曾经是个"合法的陷阱"**：它是"等任何新动态"的显式写法，返回 0 完全正确。
  但调用方**本意是等某个具体编号、却因为参数解析把编号弄丢了**时，它会拿到一个语义上正确的 0
  和一个语义上完全错误的结论（实测：两个 agent 因此各空转 5 步）。
  现在**三层都堵死了**：CLI 拒绝 `--id 0`（退出码 2），驱动层把"缺 id / 非正整数"当硬错误
  交回模型重试，`--any` 不给编号也直接报错。想要"等任何新动态"就**不写 `--id`**。

## 协作险情 —— 心跳全绿也发现不了的那类故障

心跳只证明"某个 agent 最近动过"。它**证明不了**两件事：它等的答案还会不会来、
它是不是正把预算烧在无意义的来回上。这两类故障的共同点是**看板一片健康**，
所以光靠卡死判定（看"太安静"）永远抓不到。`coordination_hazards()` 把它们统一报出来，
`hazards[]` 里的 `kind` 目前有三种：

| kind | 形态 | 为什么自己发现不了 |
|---|---|---|
| **不可达等待** | A 在等 B 回答 `#N`，B 却已写「任务完成」退出 | B 的状态是"完成"（正常），A 还在续心跳（也正常），两边都不像有问题 |
| **互相等待（死锁）** | A 等 B 的回应，B 同时在等 A 的回应 | 双方都在 await 里稳定刷心跳，谁都不会先答，两边都显示健康 |
| **通信过热** | 同一对 agent 连续交替来回 ≥ `PINGPONG_WARN`，期间无第三方插入 | 这两个正在**最积极地互相发言**；看板上他们是最健康的 |

### 数据来源一：`awaiting` 标记（等待图）

仅靠"存在一条 open 的提问"是**推不出**等待关系的 —— 提问开着不代表提问者此刻真的在等它。
所以 `await` 在阻塞期间会往共享状态写精确标记：

```jsonc
// state.agents.<name>.awaiting —— 只在 await 期间非空
{ "ids": [1, 2], "id": 1, "since": 1758... }   // id 只是 ids[0]，方便单条读取
// 退出时在 finally 里清空，唯一例外：**因互相等待退出**时不清，改写成：
{ "ids": [1], "id": 1, "since": ...,
  "deadlock": { "with": "对端名", "id": 对方等的编号, "at": ... } }
```

那个例外是刻意的（2026-09-29 实测踩出来的）：先认出环的一方如果顺手清掉标记，
对端下一轮扫过来时环已经没了 ⇒ 它只会**白等到 `--timeout`** 才超时退出，全程没人告诉它
「你们已经死锁了」。死锁是两个人的事：留标记让对端也退 5，两边都退了看门狗仍看得见这条环
（措辞会改成「双方都已收手，但提问仍没人答」）；有一方 `reply` 后，`reply` 会顺手摘掉
提问者标记里那条 id（「回应即撤掉等待」，进程不在也生效），环即破。

**deadlock 标记只递一次**：`await` 采信对端的 deadlock 标记，仅当它的 `at` 晚于
**自己这次 await 的开始**（= 我等的过程中新发生的事）且未超过 `DEADLOCK_HINT_TTL`(300s)。
没有这条限制，上一轮死锁留下的旧标记会把之后的**单向等待**误判成死锁
（自测 [43] (e) 是它的回归用例：旧标记在 ⇒ 单向等待必须仍按超时退 1）。

等待图 = `awaiting.ids` × `state.exchanges` 的 `to/from` 关系。
`<a1> → <a2>` 表示"a1 此刻在等 a2 回答"。**多路等待会给每个还没回应的目标各建一条边**，
所以"一次等三个人、其中一个已经收工"能精确点到那一个：

- `edges[A] ∋ B` 且 `B` 状态为 `完成` → **不可达等待**（key 带被等的那条编号）
- `edges[A] ∋ B` 且 `edges[B] ∋ A` → **互相等待（死锁）**

### 数据来源二：`dialogue` 流水（乒乓熔断）

`reply` 是**就地更新**已有交换的，交换表按 `id` 排出来**不是时间顺序**，
用它算"来回轮次"必然算错。所以另开一条 append-only 的点对点流水：

```jsonc
// state.dialogue —— 只记 ask/reply 这类点对点动作，不记 post（广播心跳会把信号冲淡）
{ "seq": 7, "ts": 1758…, "agent": "a1", "peer": "a2", "kind": "ask" }
```

`pair_streak()` 从最近一条**往回**数，只要每一跳都还在这两个人之间就继续数，
一旦出现第三方或用户消息立刻停 —— 所以它算的**不是**"这两人总共聊了几轮"，
而是"这两人是不是已经陷在只有彼此的回环里"。这正是"正常深挖"与"无进展互相确认"的分界。

### 两条必须成立的不变量

1. **只信"还在等待、且自身还活着"的标记**。进程被 kill 会留下过期的 `awaiting`，
   所以要求该 agent 的静默 ≤ `--stale-after` 才采信，否则丢弃
   （回归断言：自测 [25]「A 过期的等待标记不再触发险情」）。
2. **险情消失后必须能再次上报告**。`state.hazard_seen` 按 key 去重 + 冷却，
   但 key 一旦不在本轮险情里就被清掉，复发时不会因为"报过"而静默
   （第三方插话后计数归零 → 过热险情消失 → 之后再犯还会报，自测 [26] 有断言）。

### 熔断闸门（不是诊断，是叫停）

| 闸 | 阈值 | 处置 | 出口 |
|---|---|---|---|
| 乒乓 | 连续交替 ≥ `PINGPONG_WARN`(6) | 命令输出里提醒 | —— |
| 乒乓 | 连续交替 ≥ `PINGPONG_HARD`(12) | `ask`/`reply` 拒绝，**退出码 4**，不落盘 | `--force` |
| 心跳预算 | 每分钟 `post` ≥ `state.post_cap`(默认 60，`init --rate-cap` 改，0 关) | `post` 拒绝，**退出码 4**，且**不刷新 `last_seen`** | `init --rate-cap` |

心跳预算被拦时**刻意不刷新 `last_seen`**：停不下来的 agent 不是"活着"，是"空转"，
让它同时在 `stale_after` 之后被标成疑似卡死，两处报警比一处更难被忽略。

熔断是**启发式闸门**，不是诊断：它只知道"这个模式看着像失控"，
不知道你是在做必要的深挖还是在空转。所以一定留 `--force`，且提示文案直接写清下一步动作。

### 可见性

- `check` / `status` 在最显眼的位置输出 `⚠ 协作险情 N 条（心跳全绿也发现不了的那类）：`
- `check --json` 输出 `hazards: [...]`，每项含 `kind` / `key` / `agents` / `text`
- 每行 agent 状态带 `waiting_on: <id|null>`、`waiting_ids: [...]`、`posts_per_min: N`
- `format_check` 会在行尾标 `<= 心跳偏密 N/min`（预警线跟着这块看板的 `post_cap` 走）
- `emit()` 把险情写进 `alerts.md`（tag=告警），冷却 ≥60s，与卡死告警共用 `alert_seq`
- `await` 自己也会实时判定对端是否已收工：命中就**立刻**返回 3 并打印
  `✗ 对方已收工：<peer> 写了「任务完成」，#N 的答案不会来了（只等了 Xs，没白耗完 Ts）`

## 办事轴 —— 第二根观测轴（"该办的事还在不在"）

心跳轴问「它还在吗」，办事轴问「**事情丢了没有**」。两者**互不替代**，退出码都是 `1`
（都属于"业务险情"这一族，**刻意不新增码** —— 为同一类事实造第二个码会破坏
"同一类事实同一个码"这条纪律）。

存在的理由是一组实测对偶（2026-09-29，同一块真板）：

| | 心跳轴 | 真事故 |
|---|---|---|
| 那个下午 | 误报 **33** 条 | 真卡死 **0** |
| 唯一一次真事故 | **告警 0 条** | 一条提问被静默丢弃 **547s** |

调阈值救不了这个 —— 错的是**观测口径**，不是数字。看门狗原来的隐含前提是
「agent 的存在 = 它在自报心跳」，而"有人在等一个答案"这件事**根本不产生心跳**。

三层判据：

```
① 开够久     ← now - exchange.ts >= stale_open_after（`init --stale-open-after N`，默认 600s）
② 对方还答得出来 ⇒ [事故]      ⇒ check 退 1，该催 / 该自己答掉
③ 对方已收工     ⇒ [该结案]    ⇒ **不**退 1，报出来只是给提问者收尾用
```

**②③ 必须分开列**：两类处置完全相反（一个该催、一个该结案），混在一起报就是噪音，
而噪音会让整根轴被无视。这一条是被另一位 agent 纠正后才加的
（初版只有"开够久"一层，会把"对方已收工、永不会答"也报上来）。

数据来源与「协作险情」同一份：`open_exchanges(st)` 读 `state.json` 的 dialogue 流水，
**不解析 `board.md` 文本**（当天已有两处翻车在"猜一个字段 / 自己数一遍"上：
grep 数消息错 2 条、猜 `alerts[].status` 错 200 条）。

可见面（三处，口径一致）：

- `check` / `status` 单独一段：`⚠ 办事轴（阈值 Ns）：心跳全绿也发现不了的那类`，
  下面按 `[事故]` / `[该结案]` 分开列并各自给出处置建议
- `check --json` 输出 `stale_opens[]` / `unreachable_opens[]` / `stale_open_after`
- `emit()` 把**事故**写进 `alerts.md`，按 `open:#<id>` 去重，**闭环即自动清除**
  （该结案那一类**不**告警，它不是事故）

`spawn` 型与「待启动」这两个状态是**心跳轴上的豁免**，在办事轴上**没有豁免**：
一个 spawn 型 agent 被问了不答，照样是事故。这是"少报由第二根轴补回来"的落点。

## 增量探针（brief）

模型没有"被推送"的能力 —— 上下文只在它自己发起工具调用时更新。所以交流只能"拉"。
`brief` 就是那个拉手，语义是**游标增量**而非全量。

- `state.agents.<name>.board_cursor` —— 该 agent 读到看板第几条（只计**别人**的行）
- `state.agents.<name>.user_cursor` —— 该 agent 读到 user.md 第几条
- `brief --agent a1` 输出：别人的心跳 + 用户喊话 + 看门狗告警 + 全局状态一行 + 锁归属
- `--peek` 不推进游标；`post` 里的提示用 advance=False，只看不消费
- 为什么排除自己的行：自己刚写的日志从别人视角看才是信息，对自己是噪音

探针挂在 `post` 的必经路径上（每次心跳都会提示"有 N 条新动态"），
这是让 agent 真的会去看的唯一可靠办法 —— 光把命令写进文档，模型大概率想不起来调。

## 实时视图（serve）

```bash
work_log.py serve --port 8788 [--host 127.0.0.1] [--interval 3] [--no-watch]
```

| 端点 | 内容 |
|---|---|
| `/` | `assets/viewer.html`，深色页面，每 2s fetch 一次 `/api/board` |
| `/api/board` | 合并后的时间线 + agent 状态 + 锁 + 未确认告警 + **待回答提问** + **看门狗存活**（JSON） |
| `/api/health` | `{"ok":true}` |

要点：

- **合并放在服务端**（`snapshot()`），前端只渲染 —— 时间语义只有一处，
  不会出现前后端各算一套排序。
- 用户喊话按 `[HH:MM:SS]` 前缀解析后插进同一条时间线；手写且没带时间的当"刚说的"排末尾。
- `snapshot()` 额外暴露三组为"看得见"服务的字段：
  - `questions` —— 状态为 `open` 的交换，页面横幅显示「#1 a1 → a2 … 已等 12s」
  - `pending_user` —— 还没被 `ack-user` 认领的喊话
  - `last_scan_at` / `watchdog_idle` / `watchdog_stale` —— **看门狗自己多久前扫过**。
    没有这组字段时，「全员健康」和「根本没人看」在页面上长得一模一样。
  - `alerts_recent` —— 最近 6 条告警（**含已确认的**）。只给未确认的，会让「已自动恢复」
    这件事在页面上凭空消失，所以页面额外渲染成灰色「已确认」卡片留痕。
- `serve` 默认**自带看门狗线程**（`--no-watch` 关掉）。多个看门狗同时跑**不会重复写同一条告警**
  （`emit()` 在 flock 内做 `alert_open` + cooldown 判重），**但它们的阈值是各算各的、取更严的那个生效**。
  所以 `watch --stale-after 90` 配一个默认阈值的 `serve`，你仍然会在 45s 收到告警——你会以为自己
  阈值没生效（实测踩到）。**要么两边传同一个 `--stale-after`，要么 `serve --no-watch` 只留一个 watch**。
  `serve` 启动时会把实际生效的阈值打印出来，先看那个数字再判断。
- **端口被占会明确报错并退出**（`✗ 端口 8788 起不来：[Errno 48] … 换个端口：8789`），
  不会静默失败。这一点很重要：否则你会以为在验证新看板，其实旧进程还在服务另一块看板。
- 默认只绑 `127.0.0.1`。**不要改成 0.0.0.0** —— 看板包含你的项目内容。
- 响应带 `Access-Control-Allow-Origin: *`，所以直接双击 `viewer.html` 用 `file://` 打开、
  再手动指向服务也能用。


## 看板行语法

```
<agent名> HH:MM:SS [标签] 正文
```

正则：`^<([^>\s]+)>\s+(\d{2}:\d{2}:\d{2})\s*(.*)$`

- `agent名` 建议 `agent1` / `agent2` / `watchdog`（`watchdog` 保留，不参与心跳判定）
- `标签` 可省略。取值：`收到 决定 执行 阻塞 建议 告警 恢复 任务完成`
- `正文` 内的换行/连续空白会被压成单个空格
- 跨天时脚本自动插入 `## YYYY-MM-DD` 分节

例：

```
## 2026-09-17
<agent1> 19:07:12 [收到] 收到用户要求：加语音开关。我现在要改 backend/tts.py。
<agent2> 19:07:27 [决定] 用户的意思是前端加个 toggle。现在我要动 Vue 组件。不对，agent1 正在占用 tts.py，我同时改会冲突，等它搞完我再行动。
<agent1> 19:07:42 [建议] 继续改 tts.py。看到 agent2 要动前端，这其实用不上新接口，我觉得你可以试试直接复用 /api/tts。
<agent2> 19:07:57 [执行] 收到 agent1 的建议，验证可行性——/api/tts 确实够用，执行，前端直接接。
<agent1> 19:08:30 [任务完成] 语音开关默认关，测试通过。
<watchdog> 19:09:12 [告警] <agent3> 已静默 61s（阈值 45s）且未写「任务完成」→ 疑似卡死，请在线 agent 检查该 agent 是否卡死并修复
```

**手写看板是合法的，而且照样被监督**：`scan_board()` 每次都会重解析 board.md，
返回每个 agent 的最新时间戳、标签和累计条数。只在看板里出现过的 agent 会被自动纳入
监督（`note = "仅出现在看板（手写）"`），所以"绕过脚本"并不等于"绕过看门狗"。
反过来，last_seen 取 board 与 state 中较新的那个，手写行也不会被当成卡死。

## agent 名约束

`AGENT_RE = ^[A-Za-z0-9_.\-一-龥]{1,32}$`，`watchdog` 为保留名。

原因：agent 名直接进看板行首 `<名字>`，含空格或 `>` 会让 `ENTRY_RE` 解析失败，
看板反解就此失效。所有入口（`post` / `hold` / `release` / `read-user` / `lock` /
`unlock` / `init --agents` / `identity set`）都会校验并拒绝脏名字。

名字**从哪来**（`--agent` 缺省时的三档解析）见「身份」一节 —— 那是另一件事：
前者管"名字本身合不合法"，后者管"这个名字是不是**只有你**在用"。

## 判定状态机

对每个已注册 agent，每 tick 计算一次：

```
待启动    ← 从没写过任何一条心跳（entries == 0 且不在看板里）
完成      ← 最新一条日志的标签 ∈ {任务完成, 完成, done, DONE, TASK_DONE, 收工}
          或 state.status == "done"
          —— 且**没被下面两条推翻**（见「完成是一项会被推翻的声明」；
             另有第三条只是"提醒"，不改判，故不计入）
挂起中    ← expected_silence_until > now（hold 声明过，且未到期）
spawn 型  ← identities.json 里声明过 spawn（判活交给它的驱动层，不按心跳告警）
疑似卡死  ← 非以上者，且 stale_after < (now - last_seen) < agent_offline 分界
离线      ← 非以上者，且 (now - last_seen) ≥ max(3600s, 20 × stale_after)
            （「疑似卡死」档内按**时长**细分出的子档：判据就是模块级 agent_offline()，
              告警措辞 / status 状态表 / 网页徽章三处共用 —— 判据只能有一处）
已离场    ← state 里带 `retired` 标记（`retire` 宣告过「它不会再回来」）
            —— **最高优先级**：不再判卡死、不再发告警；它 post 一条即自动复位
            —— 且**人看的输出一律不显示**（状态表 / 网页 / tick 行 / brief 汇总；
               数据层不删：`--json` 仍含它，`retire --undo` 与驱动层还要用）
心跳中    ← 其余
```

优先级：**已离场 > 待启动 > 完成 > 挂起中 > spawn 型 > 疑似卡死/离线**（离线与疑似卡死同层：
同一个上游条件——静默超阈值且未收工——只是**措辞与处置动作**不同）。这个顺序是刻意的：

- **待启动排第一**，是为了把"名字写错"和"真的卡死"彻底分开。`read-user --agent agnet1`
  这种手误也会注册出一个 agent，如果它参与卡死判定，看板会被误报淹没。现在它只是安静地
  显示「待启动 / 从未写过心跳」，`check` 在页脚单列一行提示。**待启动永不产生告警。**
- **完成第二**：写完「任务完成」的 agent 彻底退出被监督范围，它不心跳是正常的。
- **挂起中第三**：声明了长任务的 agent 也不该被吼。
- **spawn 型第四**：它的"存活"本来就由驱动层证明，心跳不是它的证据。它**不进 `stale`**，
  但照样留在状态表里、照样被办事轴盯着 —— **"少报"不是靠它自己兜，是靠第二根轴补回来。**

### ★ 完成是一项会被推翻的声明（它会同时关掉两根轴）

完成状态不是"写过的标签"，是**此刻是否成立的事实**。它之所以必须收紧，是因为它同时是两个
语义的开关：对**心跳轴**是「别报我卡死」，对**办事轴**是「我不会再答了」。一个循环进程
（守护 / 监听 / 看门狗）把心跳打成「任务完成」，就一次性拿到两份豁免，
**而板上完全看不出来** —— 2026-09-29 真有一个这样的守护进程跑了半小时，
期间所有问它的提问都被办事轴归成「该结案」（也就是'不用管'）。

**推翻它的两条规则**（都是结构性的，不需要谁声明）：

| 规则 | 判据 | 需要谁配合 |
|---|---|---|
| ① 它自己又说了话 | 最新一条日志不是完成标签 ⇒ 它回来了，完成作废 | 无（结构性） |
| ② 它声明过自己是循环型 | `identity set --loop` ⇒ 声明优先于标签 | 要人声明（可能忘） |

① 兜住"完成之后又被叫回来干活"这条合法路径 —— 完成是**声明**、不是终态。
② 精确，但要人记得声明。对**忘了声明**的，引擎还有一条 **提醒**（注意：只提醒、不改判）：

- 尾部连续 ≥3 条完成标签（`REPEAT_DONE_N`）**且**相邻两条间隔 <「办事轴」窗口
  （`REPEAT_DONE_WINDOW`，默认 600s）⇒ 在 `status` / `check` 里点名提醒一次，
  **不动它的完成状态**。

**为什么只提醒 —— 这一版是被真板打回来的。** 第一版写的就是"≥3 条 ⇒ 完成作废"，
上线当场误伤了一条**正常工作的交互会话**：它每个用户回合收工一次、工作期间不发中间
心跳，尾部本来就会连着好几条完成（实测三条间隔 29~83 分钟），被判成循环后当场开始
被读成异常。**而那种形态恰恰是本项目最主要的用法。**
**一条会惩罚主要使用形态的规则，比它堵的那个洞更糟。** 引擎分不出"勤快的会话"和
"守护进程"，就不该替人猜：密度那一维（循环像心跳、分钟级；真收工按回合来、十分钟以上）
只能把误判压小、压不到零，所以最终形态是**提醒 + 把判定交给声明**。
取 3 不取 2 的理由同上：两次还能被「驱动层重试了一次 `--done`」解释（命令超时后重发
很常见，属于调用方的正常行为）。

**办事轴的判据完全押在这个 state 上**（`_peer_can_answer` 只问"它是不是完成"）。
所以想改办事轴的人请注意：**该改的是上面这个推导点，不是 `_peer_can_answer`** ——
否则两根轴会用两套不同的"完成"定义，而那种不一致不报错。

默认阈值：心跳周期 15s，`stale_after` 45s（3 个周期），告警冷却 135s，
`stale_open_after` 600s（办事轴：提问开多久算没人办）。

## 告警状态机

```
静默超阈值 ──► alert_open=true, alert_repeat=1, 写 alert 记录 #id, 写 board + alerts.md
                 │
                 ├─ 继续静默，且距 last_alert_at 超过本次间隔
                 │     ├─ 前 3 次：按 cooldown 重复（"仍无心跳…请直接接管"）
                 │     └─ 之后：**指数退避** 135 → 270 → 540 … 上限 3600s
                 │           （退避间隔按"报了几次"算；措辞档位另按下方的时长判据，
                 │             两件事刻意解耦）
                 │
                 └─ 该 agent 再次 post
                       └─► 下一 tick 写 <watchdog> [恢复]，把它所有未确认告警
                           自动置为 acked_by="watchdog:auto-recovery"，且 alert_repeat 归零
```

- **去重**：`alert_open` 为真且未到本次间隔时不再重复写，避免刷屏。
- **退避**：一个离线 agent 若永远按 `cooldown` 重复，噪音会**反过来把真信号埋掉** ——
  实测某板 42 小时攒出 **994 行 watchdog vs 110 行实质发言**，「另一个 agent 真的停了」
  这件事被彻底淹没。所以重复 `ALERT_BACKOFF_AFTER(3)` 次后按
  `ALERT_BACKOFF_BASE(135s) × 2^k` 退避，上限 `ALERT_BACKOFF_CAP(3600s)`：
  同一场景从 ~1120 条降到 ~45 条。退避基数**刻意与 `--cooldown` 解耦**（只取 `max`），
  否则有人把 cooldown 调成 0，就等于把退避也一起关掉了。
- **措辞分档**：静默 2 分钟说「疑似卡死」（值得去救），静默到小时量级说「离线」（人已经不在了）。
  两者处置动作相反，共用一句话会让人去救一个不存在的进程。
  **判据是时长、且全项目只有一处**：`agent_offline(silence, stale_after)`
  = `silence ≥ max(3600s, 20 × stale_after)`（1 小时是"小时量级"的下限；20× 是让阈值被调大的板跟着抬）。
  ⚠ 旧实现曾按 `alert_repeat ≥ 3`（报了几次）在告警正文里翻档——几分钟就升格，会把一个
  可能真卡死的 agent 过早说成"人已经不在了"；且 `status` 状态表 / 网页徽章根本不知道这一档，
  同一个 agent 一屏两种说法、旁边还挂着对已消失进程毫无意义的「补 hold」按钮（2026-09-30 用户截图抓到）。
  现在状态机在「疑似卡死」档内按它细分出「**离线**」子档，三处共用同一个函数；
  `check` 退出码不受影响（工作可能真丢了，离线照样进 `stale`、照样告警）。
  告警里的时长统一走 `fmt_dur()`（`152778s` → `42h30m`）—— 静默时长正是选择处置动作的依据，必须可读。
- **离线 ≠ 已离场：猜 vs 拍板**。「离线」是引擎按时长**猜**的 —— 可能猜错（它也许下一小时就回来），
  所以工作可能真丢了、照样进 `stale` 照样告警，只是措辞换成"别去救"。但**猜**解决不了
  「确定永远不会回来」的 agent：告警按 1h 退避上限**永远重复**（每只每天 ~24 条），板上永远挂着行，
  每条都在建议"等它回来"——而它不会回来。所以还需要人**拍板**的出口：`retire` 宣告「已离场」，
  告警就此停（名下未确认告警一并确认），宣告错了复位也很便宜（它一条 post 即自动撤销，或 `--undo`）。
  离场**不是删除**：state 条目原样留着，历史可 `prune` 归档。
  宣告之后**人看的输出一律不再显示它**（状态表 / 网页 / 看门狗 tick 行 / brief 汇总）
  —— 都说了不会再回来，就别再占板面；数据层保留（`--json` 仍含、`--undo` 可撤）。
- **自动闭环**：agent 活过来 → 告警自动关闭，不需要人手动 ack。
- **人工 ack**：`ack --by a2 --agent a3` 用于"我接管了，别再报它了"。
- **上限**：`state.alerts` 只保留最近 200 条（`MAX_ALERTS`），长会话下不会无限增长。
- 每 tick 只写一次，快照在进程内完成，不会同一轮重复写同一条。

## 接入片段（onboard）—— 「第二个 agent」是怎么被拉起来的

「接入」是**两件**事，自动化程度恰好相反：

- **机械接入（工具侧）本来就自动。** `post` 对未知 agent 名**当场注册**（`_get_agent`），
  根本没有 `join` 子命令；它那一次 `post` 让 `others` 非空、顺带触发 `auto_ui`
  （起 `serve` + 弹浏览器，而 `serve` 默认自带看门狗）。**这一半不需要任何额外动作。**
- **认知接入（它那侧）不可能自动。** 模型没有推送通道 —— 上下文只在它**自己**
  发起工具调用时才更新。唯一办法，是让义务句落进它**启动时一定会读到**的文件里。

`onboard` 负责后半段的「交付」。落点判断它**刻意不替人猜**（猜错比不猜更糟 —— 见下），
但"要证据"不等于"要人去查"：`--detect` 会**观测**本机装了哪些工具链并打出证据，
`--to auto` 按观测结果逐个落跨目录档。

| 目标 | 落点 | 对谁有效 |
|---|---|---|
| `--to user` | `~/.workbuddy/MEMORY.md` | WorkBuddy 会话 —— **跨工作区、每会话注入 ⇒ 唯一真正通用的落点** |
| `--to opencode-global` | `~/.config/opencode/AGENTS.md` | opencode —— **任何目录**开会话都读 |
| `--to claude-global` | `~/.claude/CLAUDE.md` | Claude Code —— 跨目录 |
| `--to repo` | `<cwd>/AGENTS.md` | 在**该仓库**启动的 opencode / Codex / Cursor 会话 |
| `--to claude` / `gemini` / `cursor` | `<cwd>/CLAUDE.md` · `GEMINI.md` · `.cursor/rules/work-log.mdc` | 同上（各自系） |
| `--to <路径>` | 任意文件 | 你自己判断 |
| `--to auto` | **探测结果决定** | 只落跨目录档（`opencode-global` / `claude-global`；`--include-user` 才加 `user`） |

### 落点探测（`--detect` / `--to auto`）—— 把人工取证变成一次观测

装过的工具链一定在机器上留下痕迹，所以落点是**可观测的**。两条命中判据都是观测而非推测：
配置目录存在（`~/.config/opencode` / `~/.claude` / `~/.cursor` / `~/.gemini` …），
或可执行文件在 `$PATH` 上。输出里每条都带**命中的路径**作为证据 ——
「我探测到了」如果不可查验，就只是把口头约定换了个地方。

```bash
python3 "$WL" --dir "$DIR" onboard --detect        # 只探测、不写盘
python3 "$WL" --dir "$DIR" onboard --to auto       # 探测 + 逐个落跨目录档
```

三条口径：

- **只落跨目录档。** `--to auto` 不会落 `repo` / `claude` / `gemini` / `cursor` ——
  那几档必须知道「对方在哪个目录启动」，而这是探测不出来的。跨目录档不看 cwd，
  于是这个查不到的事实被整个绕开。
- **`user` 默认跳过**（`--include-user` 才落）。它每会话、每工作区都注入；
  一块只服务某个项目的板，把坐标写进用户级记忆等于把 A 项目的板告诉 B 项目的会话。
- **探测到却落不了的，必须说出来。** Cursor / Gemini CLI 只有仓库级落点 ⇒
  `auto` 会列出来并给替代命令，**不静默忽略**。
- **`--to auto` 一个可落的都没探测到时退 `1`**（业务：什么都没达成），
  而**不是** `2` —— 「这台机器上没装能自动落的工具链」不是用法错误。
  用错别名才退 `2`。

三条不变量：

1. **默认只打印，什么都不写** —— 连看板目录都不会顺手建出来（`--dir` 解析走 `mkdir=False`）。
   一个号称 dry-run 却会 mkdir 的命令，是最不划算的那种"方便"。
2. **落盘幂等**：只替换 `<!-- work-log:begin -->` … `<!-- work-log:end -->` 之间的内容，
   块外一字不动。所以它能反复跑，也能跟着仓库进版本库。
3. **目标里已有「指向本板的异己协议」时默认拒绝并退 `2`**（给了本板坐标、或提过 `work-log`，
   却没有标记块）—— 硬追加会留下两份互相打架的协议、而且没人知道哪份是权威。
   要追加必须显式 `--force`。
4. **批量落盘先预检**：`--to auto` 会在**一个字节都不写**之前把所有落点验一遍，
   任何一个会被拒就整体不落。半落状态比全不落难收拾得多 —— 没人知道哪几处生效了。
   ⚠️ 判据**不能**只认字面量 `work-log`：实测手写的那份只写了「看板：`<路径>`」、
   压根没提工具名，只查工具名会把它静默追加成两份（回归组 `[35]` 抓到的真洞）。

**第四条不变量（2026-09-25 补）：片段里不许出现引擎的本机绝对路径。**
片段的作用是**离开这台机器** —— 它会被抄进对方的记忆文件、会被拷到别的电脑。
写死 `/Users/<某人>/…/work_log.py` 的那一刻，这段协议在第二台机器上就是死链，
而且失效是静默的：对方照抄、报个"文件不存在"，然后**不再报到**（正是本节开头那个事故的复现路径）。
现在片段只留**看板目录**（它本来就是数据、跟着板走）+ 板里的引导脚本 `<看板>/worklog`；
脚本负责现场解析引擎位置。回归组 `[36]` 用「片段里不许出现 `/Desktop/work-log-`
或 `.workbuddy/skills/work-log`」把这条钉死。

**与 `doctor` 的关系**：片段天生带「坐标 + 报到义务」，因此**必然能通过 `doctor ③`** ——
两侧共用同一道门槛 `_mentions_board()`。这是刻意的：**开药与验药必须用同一把尺**，
否则就会出现「自己开的药、自己验不过」这种最难查的错（回归组 `[35]` 把这条钉住了）。

那道门槛的判据（回归组 `[38]`、`[39]` 守）。**先有一条前提**：这看起来得**确实像个路径** ——
`~` 后面必须跟分隔符（`~/x`、`~用户名/x`），而且它**展开得开**、展开后是**绝对的**。

1. **字面形态**（`_literal_forms()`）：`str(d)` 与它的 `~/…` 写法直接出现在文本里 ——
   快路径，不碰文件系统，覆盖绝大多数情况。**别单独用它做判据**（见下）。
2. **归一化形态**：把文本里每一段像路径的 token 先 `os.path.samefile()`（按 inode + 设备号，
   一次覆盖符号链接、**大小写差异**、挂载别名），不成就退回 `Path.resolve()` 归一后比字符串
   （给还不存在的路径兜底）。

**为什么"前提"本身也得当判据**（回归组 `[39]` 守）：`_PATH_TOKEN_RE` 过去以**裸 `~`** 起头，
于是中文行文里的**约数波浪号**（`~90%`、`~2.4s`、`~0.9-3s`）被吃成路径 token，而它展不开 ——

- `Path("~90%").expanduser()` 抛 `RuntimeError`（**不是** `OSError`，`except OSError` 接不住）
  ⇒ 一路冒到 `main()` 变成 **`70`（内部错误）**，一个约数把体检打成"工具坏了"。
  真机 `~/.workbuddy/MEMORY.md` 里就写着这三行（2026-09-25 实测）。
- 只吞异常**更坏**：展不开会**原样保留**，`resolve()` 把它当**相对路径**接到 cwd 上 ——
  板恰好建在当前目录时，`<cwd>/~90%` 与板前缀匹配 ⇒ 一句「延迟 ~2.4s」
  就把这份记忆判成"提到了本板"（**静默假绿**）。

所以判据只在"看起来确实是路径 **且** 展开得开 **且** 展开后是绝对的"时才下结论。
方向刻意选**宁可漏、不可猜**：漏了只是多跑一次 `onboard`，猜了是一条没人会发现的假绿。
同类修正也用在两个命令行入口上：`--dir` / `--to` 里写展不开的 `~` 退 **`2`（用法）**，不是 `70`。

为什么必须有第 2 条：`resolve_dir()` 总是把 `d` 归一成已解析形态，而手写协议里常是未解析拼法。
实测（2026-09-25）板在 `/private/tmp/x`、手写文本写 `/tmp/x` —— 同一个目录、两种写法，
A/B 只改拼法就得到两种结论：`onboard` 本该拒绝却退 0 并**静默追加出第二份协议**，
`doctor ③` 明明有坐标却判「一处都没有」。两个判据都错，且都不报错。

刻意**只认"完全相同"或"在其之下"**，不认"尾巴相同"：只认 `/.workbuddy/work-log` 这种尾巴
会命中任何一块板，"我有坐标"就退化成一句永远为真的废话。反面对照（只提父目录 ⇒ 不误拒）
在 `[38]` 里也有断言。

## 身份：名字怎么固定，以及为什么必须固定

`_get_agent(st, name, t)` 按名字取的是 `st["agents"][name]` —— **同一个 dict**。
于是两个会话叫同一个名字时，它们共享 `last_seen` / `entries` / `board_cursor` /
`user_cursor` / `awaiting`。后果不是"名字不好看"，而是：

- 看门狗看到的是**两个人交替刷新**的 `last_seen` ⇒ **谁都不会被判卡死**；
- `entries` 是两个人的合计 ⇒ 「待启动 / 从未写过心跳」判据失效；
- `awaiting` 被后写的人覆盖 ⇒ 等待图画出的是错的边。

而且**板上完全看不出来**。这是整套判断（谁卡死、谁在等谁）唯一的地基，所以它值得单独设一道闸。

### 三档解析（`resolve_agent`）

`--agent` 缺省时按顺序取第一个成立的，任何一档都不成立就**退 2**并打印可抄的命令 —— **绝不猜**：

| 档 | 来源 | 换会话 | 换目录 | 换电脑 |
|---|---|---|---|---|
| 1 | 命令行 `--agent` | ✗ | ✓ | ✓ |
| 2 | `$WORK_LOG_AGENT` | ✓（同一驱动层） | ✓ | ✗ |
| 3 | 板上 `identities.json` 里 `cwd == 我当前目录` | ✓ | ✗ | ✓（跟着板走） |

刻意**没有**「板上只有一个名字就用它」这条规则：那会在第二个 agent 还没登记的窗口期
把它静默塞进第一个人的身份里 —— 正好是最该拦住的时候。

### 登记表（`identity`）

`identities.json` 形状：`{"<名字>": {"cwd", "kind", "purpose", "since"}}`，
跟着**看板**走（不是跟着机器走）。`identity set` 的三条语义：

1. **别的 `cwd` 已经占了这个名字 ⇒ 拒绝退 2**，并把占用者的目录打出来。
   （这就是"两个会话共用一个身份"的入口闸。`--force` / `$WORK_LOG_FORCE_IDENTITY=1` 是
   "你确实换了目录"的逃生口 —— 它的语义是**把这条登记改到我现在这个目录**。）
2. 同一 `cwd` 可以登记多个名字（比如一个目录里真的跑着两个会话），
   此时**任何**自动解析都会因为歧义而退 2 —— 那两个会话必须各自显式传 `--agent`。
3. `whoami` 把「我叫什么、凭什么」打出来。身份固定这件事如果不可查验，
   就只是又一句口头约定。

### 为什么名字不能写在共享文件里

`AGENTS.md` / `CLAUDE.md` 会被**任何在该目录启动的 agent** 读到。在里面写死 `--agent a1`，
等于给所有会话发了同一个身份 —— 正是上面那组失效。共享文件里只写
**义务 + 看板坐标 + 名字从哪来**；名字本身交给环境变量或登记表。

## 可移植：引导脚本与 `.worklogrc`

`init`（以及任何一次 `ensure_files`）会在看板目录里落一个可执行的 **`worklog`** 引导脚本。
它干三件事：钉死 `--dir`、**自己找引擎**、设 `$WORK_LOG_SELF`（让引擎打印的提示行
也指向板里的脚本，而不是引擎在本机的位置）。

查找顺序（先命中先用）：

```
$WORK_LOG_BIN  →  <看板>/.worklogrc 的 WORK_LOG_ENGINE  →  <看板>/work_log.py
              →  <看板>/scripts/work_log.py  →  ~/.workbuddy/skills/work-log/scripts/work_log.py  →  $PATH
```

全找不到就**退 70 并打印三条修法**（设 `WORK_LOG_BIN` / 写 `.worklogrc` / 把引擎拷到板旁边），
而不是抛一句语焉不详的报错 —— "告诉人怎么修"比"报个错"贵不了多少，但省掉一整轮排查。

`<看板>/.worklogrc` 是**本机私有**的（`init` 同时在看板目录放了只含它的 `.gitignore`）。
它写成 `export WORK_LOG_ENGINE="${WORK_LOG_ENGINE:-<本机路径>}"` —— 这个 `${VAR:-…}` 是刻意的：
**环境里显式给的值优先**，否则会出现「我明明 export 了新的引擎位置，它却还在跑 rc 里那个旧的」。

## 退出码约定（便于脚本化判断）

**这个表就是对外契约，Engine 顶部有一组 `EXIT_*` 常量与之对应。**
一条铁律：

> **`1` 是业务码（超时 / 有卡死），用法错误一律 `2`。**
> 用法错误绝不能借用 `1` —— 那样「我把编号写错了」和「对方不配合」在调用方看来一模一样，
> 一个工具用法问题会被读成一条业务事实，然后基于它继续往下做。这是踩过的真坑。

| 命令 | 码 | 含义 |
|---|---|---|
| `check` | 0 | 全员健康（待启动 / 完成 / 挂起都不算异常，**且没有协作险情**） |
| `check` | 1 | 至少一个 agent 疑似卡死 / 离线（离线不豁免：工作可能真丢了），**或存在协作险情**（不可达等待 / 互相等待 / 通信过热）。
  险情必须计入：`[互相等待]` 是真死锁，心跳全绿、没有任何进程崩溃，但团队已经不往前走了 ——
  若这种情况下仍退 0，脚本里 `check || 告警` 会把它整个漏掉，而它正是这套机制最想抓的故障。 |
| `lock` / `unlock` | 0 | 成功 |
| `lock` / `unlock` | **3** | 资源被别的 agent 占用（未加 `--force`） |
| `ack` | 1 | 没有匹配的未确认告警（**业务结论**：没你的事，不是错误） |
| `ask` | 0 | 成功（**即使目标 agent 从未出现过也返回 0**，只打警告：A 经常比 B 先启动，提问早于对方首次心跳是合法的） |
| `ask` / `reply` | **4** | **被通信熔断拦下**（不是参数错，是机制叫停）—— 收敛，或加 `--force` |
| `post` | **4** | **心跳预算熔断**（一分钟内超 `post_cap`）—— 去查你的循环条件 |
| `await --id N,M,…` | 0 | 达成（全部拿到；`--any` 时任一拿到） |
| `await --id N,M,…` | **1** | 超时仍有未达成的（**绝不能当作"已回复"**，这条有回归断言）；回复里会列出还缺哪几条 |
| `await --id N,M,…` | **3** | 未达成的目标**全部已收工** → 这些答案**永远不会来**，立刻收手（不空耗超时） |
| `await --id N,M,…` | **5** | **互相等待**：你要等的人正在等你（双方各卡在自己的 await 里，谁都不会先答）→ 立刻收手，**先回答它**再回来等；处置动作与 `1` 相反（超时可以催/换人，死锁必须有一方先 reply） |
| `await`（无 `--id`） | 0 | 等到了任何新动态（别人的心跳 / 用户喊话 / 告警） |
| `doctor` | 0 | 通道已落好（cwd 有指令文件 · 记忆里**本板坐标 + 报到义务**齐备 · 我最近在报到 · 名字定得下来 · 告警没盖住发言） |
| `doctor` | 1 | 上面至少一项没落好。三类典型病：① 记忆里只有工具名 `work-log`、**没有这块板的路径**；② **有坐标却没有义务句**（"我知道有这个工具"，但没人告诉过"我必须去报到"）—— 后者更隐蔽，因为**它看起来像是已经接好了**；③ **连自己叫什么都定不下来**（没 `--agent`、没 `$WORK_LOG_AGENT`、板上也没登记本目录）—— 这条刻意只把"定不下来"算病：显式传 `--agent` 是能当场工作的，只是换了会话要重来 |
| `doctor` | **2** | 该目录没有 `state.json`（板没 init 或 `--dir` 指错）—— 用法问题，**不伪装成业务码 1** |
| `onboard` | 0 | 片段已生成（默认打印）/ 已写入目标 |
| `onboard` | **1** | `--to auto` 在本机**一个可自动落的跨目录落点都没探测到** —— 业务结果（什么都没达成），**不是**用法错误；它会打印三条可操作的路 |
| `onboard` | **2** | `--to` 指到目录、指到工具自己、别名写错、agent 名不合法，或**目标里已有一份指向本板但不是本工具维护的协议** —— 全是用法问题，**不伪装成业务码 1** |
| `identity list` | 0 | 永远 0（只读） |
| `identity set` | 0 / **2** | 登记成功 / **名字已被别的目录占着**（未加 `--force`）、没给 `--agent`、名字不合法 |
| `identity rm` | 0 | 删除成功；本来就登记过没这条也退 0（打一行说明） |
| `whoami` | 0 / **2** | 身份定得下来（含"是**哪一档**定下来的"）/ 定不下来 —— 同样是用法问题，不借 1 |
| 任意 agent 类命令 | **2** | `--agent` 缺省且三档解析全不成立（→「身份」一节）。**不猜**：猜错会让两个会话共用一个状态对象 |

> `③` 除了「坐标 + 义务」，还看**落点**：只有用户级那份（如 `~/.workbuddy/MEMORY.md`）是
> **跨工作区**的；项目级记忆长在 `<某工作区>/.workbuddy/memory/MEMORY.md` 下 —— 换个工作区
> 就是另一个文件，写在那里约等于写进一次性文件。
> 「义务只落在项目级」**不算病**（当前工作区确实能连上），但会打一条警示：
> 那是"换个目录开新会话就断"的预告（2026-09-24 实测踩到）。

### 用法 / 前置条件错误 —— 一律 `2`（`EXIT_USAGE`）

以下全部**只退 2，绝不退 1**（回归组 `[29]` 逐条锁住了 18 种）：

| 场景 | 例子 |
|---|---|
| 非法 agent 名 | 含空格、含 `>`、用了保留名 `watchdog` |
| 定不下身份 | `--agent` 没给、`$WORK_LOG_AGENT` 没设、板上 `identities.json` 也没有「本目录 ← 某个名字」（含"本目录登记了多个名字"这种歧义） |
| 空文本 | `post/reply/ask --text ""`（空心跳比不写更坏，它会骗过看门狗） |
| 编号问题 | 编号不存在 / 已被答过 / **不是被问的那一方** / `--id 0` / 越界 `ack-user` |
| 自问自答 | `ask --to` 自己 |
| 多路等待写错 | `--any` 却没给 `--id` |
| 环境参数错 | `--stale-after 0`、`--dir` 指向一个普通文件、`--resource ""` |
| argparse 层 | 不认识的子命令、缺必填参数、`--id 0` |

### 其他

| 命令 | 码 | 含义 |
|---|---|---|
| 任意命令 | **70** | **工具内部错误**（`EXIT_INTERNAL`，软件 bug）。刻意与 1 分开：1 是"业务结论"，调用方会据此下判断；工具自己坏了必须另立一码，看到 70 就去看 traceback |

`await` 的 1 和 3 都是"失败"，但成因完全不同，调用方的处置也完全不同：

- **1（超时）**：对方还活着，只是没答。可能它在忙、也可能它根本没打算答 → 值得再催或换人。
- **3（不可达）**：对方已经收工，**再等多久都不会有答案** → 唯一正确的动作是自己拍板往下走。

把两者混成同一个码，调用方就只能一律"再等等"，而那正是白等超时的来源。
驱动层（`llm_agent.py`）对 3 的处理是明确告知模型"别再等，自己拍板"；对 4 是"收敛或 `--force`"。

**为什么单独留一个 70**：这条是实测踩出来的 —— `cmd_await` 里一处残留变量名让命令抛
`NameError`，进程以 1 退出，而 1 的含义是"超时"，于是调用方会得出"对方没回"这个
**完全错误的业务结论**。工具自己的 bug 不能伪装成业务结论。

## 用户喊话通道

`user.md` 每行一条，两种写法都认：

```
[19:40:12] 用户：语音开关记得默认关，别吓到人
别动数据库
```

解析正则优先匹配 `^\[HH:MM:SS\]\s*(who)[：:]\s*(body)$`，不匹配就整行当正文。
`#` 和 `>` 开头的行视为注释忽略。

**每 agent 独立游标**：`state.agents.<name>.user_cursor` 记录该 agent 读到第几条。
`read-user --peek` 不推进游标（用于"我先看看但还没处理完"）。

## 用户对话（人类是一等参与者）

`用户` 是**人类在对话里的保留身份**（常量 `USER_NAME`）：

- **agent → 人**：`ask --agent <你> --to 用户 --text "…"`。这条交换走和普通提问完全
  相同的数据结构（`exchanges`），所以提问者的 `await` **原生**能等到人的回答，
  「对端已收工」检测对它天然安全（`用户` 永远不在 by_name 里，不会被误判收工）。
- **人 → agent**：`reply --agent 用户 --id N --text "…"`。这是 `reply` 唯一允许
  `--agent 用户` 的地方（`check_agent_name(allow_user=True)`）；其余命令对「用户」
  一律退 2 —— 防止某个 agent 叫这个名字冒充人类。
- **豁免熔断**：乒乓计数、通信过热告警、ask/reply 的渐进提醒都跳过含「用户」的对。
  人机来回不是"两个模型互相确认"，熔断人类等于把用户挡在对话外面。
- **可见性**：`status` / `check` 列出所有问向用户的待答提问，附上现成的回答命令；
  `serve` 页面的「提问」区同样显示，帮助区写明回答方式。

## 多人协作感知（启动条件）

「在干活」的判定 = agent 状态 ∈ {心跳中, 挂起中}（已开工、未收工、静默未超阈值）。
**待启动 / 完成 / 疑似卡死（含「离线」子档）/ 已离场都不算** —— 没派的、收工的、卡死的、人已经不在或宣告离场的都不是"在协作"。

- `evaluate()` 产出 `collab = {count, agents, active, required=2}`；
  `check --json` / `status --json` / `serve` 的 `/api/board` 都带这个字段。
- **切换事件**由 `emit()`（即任何非只读扫描：`check` / `watch` / `serve` 内置看门狗）
  写入看板，`<watchdog> [协作] …多人协作模式开启`；用 `state.collab_started` 标记保证
  开/关各只写一次，全员停止后复位，可以再次触发。
- **post 反馈**：`post` 时若发现同板还有别人在干活（last_seen 新鲜度 ≤ 4 个心跳周期），
  输出 `🤝 多人协作中：<名单>（在线 N）`。

## 资源锁语义


`state.locks = { "<resource>": {"agent": …, "ts": …, "note": …} }`

- 键名由调用方自定，建议用真实冲突面：`backend/tts.py`、`port:8000`、`gpu`、`vite-build`
- **抢锁失败也会往看板写一行**（`<agent2> 想占用 X，但 <agent1> 正持有，先等它释放`）：
  让"谁在等谁的锁"变成共享可见的事实 —— 这正是多 agent 协作里最容易失联的信息。
- `locks` 显示持有者静默秒数；静默 > `2 × stale_after` 时提示 `⚠ 持有者疑似卡死，可 --force 抢`
- 锁**不会自动过期**（故意）：自动过期会让两个 agent 同时以为拿到锁，那才是真正的数据损坏。
  回收必须由人/agent 显式 `--force`。
- **接管纪律**：救人的 agent 一律用**自己的名字**跑命令。`lock --agent <卡死的agent>`
  会以它的名义写一条心跳、把它"写活"，反而掩盖真实状态（压测中实测复现过这个坑）。

## 轮询开销（实测）—— 为什么不做事件流

`await` 是**轮询**的（每 `--interval` 秒扫一遍状态），所以"要不要改成 inotify / kqueue 事件驱动"
迟早会被问。先看数字（2000 行看板 / 75KB state，Mac 本机）：

| 环节 | 修之前 | 修之后 |
|---|---|---|
| `scan_board`（读 + 逐行解析） | **34.3 ms** | **11.4 ms** |
| `load_state`（75KB JSON） | 1.2 ms | 1.2 ms |
| `save_state`（原子写） | 2.0 ms | 2.0 ms |
| 单轮合计 | ~37 ms | **~14 ms** |

热点在 `board_entries` 里的 `datetime.strptime`：**每行一次通用日期解析**，占了单轮的 97%。
改成"日期段算一次本地 0 点基准 + 整数加法"后降到 11.4ms（3×）。
这不是微优化：`await` 每轮都要扫全量看板，而看板在一个真实会话里上万行很正常。

端到端（修之后）：

| 场景 | 实测 |
|---|---|
| 默认 `--interval 2`，2000 行看板，等 20s | **0.47s CPU / 20.5s = 单核 2.3%** |
| `--interval 1`（激进），等 10s | 0.41s CPU / 10.5s = 单核 3.9% |
| 6 个并发等待者，`--interval 1`，10s | 合计 2.54s CPU / ~10.6s 墙钟 = 单核 24%（每人 4%） |

**结论：不做事件驱动。** 理由不是"实现难"，是**优化错了地方**：

1. **被优化的东西在关键路径上不重要。** 事件流能把唤醒延迟从 ≤2s 压到 ~0，
   但 agent 拿到唤醒之后还要走一次完整的模型往返（实测 30~60s）。2s 是 30~60s 的 3~7%。
2. **代价是真实的。** `kqueue`(macOS) / `inotify`(Linux) / `ReadDirectoryChangesW`(Windows)
   是三套互不兼容的代码，而 Windows 上还会退化 —— 这个 skill 的卖点就是"零依赖、纯标准库、跨平台"。
   拿一个可测量的"不重要"去换一个确定的移植性风险，不划算。
3. **实测成本本来就不是问题。** 单核 2.3%，6 个并发等待者也只有 24%，
   而且随人数**线性**增长（没有锁竞争放大：6 个并发下零错误、每人与单人同量级）。

**顺手修掉的那个热点才是真的**（34ms → 11ms，3×），且它不只惠及 `await` ——
`post` / `check` / `brief` / `watch` / `serve` 全都要扫看板。

### 这条优化怎么防退化

时间断言会随机器负载抖，所以回归用**语义断言**：把 `wl.datetime` 换成一个会计数的子类，
扫一遍看板后断言 `strptime` 的调用次数 **只跟日期段个数有关**（≤8），
与行数无关（自测 [28]）。旧实现会是 3000+ 次，这个断言会当场抓住。
同一个用例还锁住"历史日期段的行必须按它自己的日期算时间戳"——
不然"修快"很容易顺手"修错"。

## 历史归档（`prune`）

`board.md` / `alerts.md` / `state.alerts` 都是**只增不减**的。真看板实测（2026-09-28）：
board.md 607KB / 2606 行、alerts.md 400KB / 2001 条、`state.alerts` 47KB。
`doctor` ⑤ 会报出噪音比，但只诊断不处置 —— 处置就是 `prune`。

```
prune [--days 7] [--keep-alerts-md 200] [--apply] [--json]
```

默认**只试算**（报告"将要发生什么"，一个字节都不落盘），确认后加 `--apply`。
**它是搬家不是删除**：搬走的内容写进 `archive/board-rotated-<日期>.md` /
`archive/alerts-rotated-<日期>.md`。（同样的 `moved_to` 路径也会出现在 `--json` 输出里。）

| 规则 | 动作 | 边界 |
|---|---|---|
| ① `state.alerts` | 已确认且早于 `--days` 的整条丢掉；已确认且早于 1 天的把正文截短（只留 `→` 之前那半句） | **未确认的永不触碰**（那是待办） |
| ② `alerts.md` | 只留最近 `--keep-alerts-md` 条，其余搬进 `archive/` | 表头行（`#` / `>` 开头）永远留着 |
| ③ `board.md` | 把 `--days` 天之前的**整段日期块**搬进 `archive/` | 最后一段（今天那段）无论如何留着；板头那几行（`#` / `>`）留着 |

### 两条不变量（都有自测锁着，[40] 组）

- **`board_cursor` 必须跟着前移。** 它存的是 `len(board_entries())` —— 一个**数组下标**，
  不是时间戳。搬走 N 条后，原来读到 2200 的 agent 游标还指着 2200，而板只剩 400 条
  ⇒ `entries[2200:]` 恒为空 ⇒ 那个 agent **从此静默收不到任何新动态**（`brief` 只会说
  "没有新动态"，看着像别人没说话）。所以 `--apply` 会把每个 agent 的游标减掉**实际搬走的
  **条目数**（不是行数），报告里写明"搬走 N 条心跳 ⇒ 同步前移 M 个 agent 的读取游标"。
  `user_cursor` 不受影响（它是 `user.md` 的消息索引，与板行号无关；`prune` 不碰 `user.md`）。
- **读板 → 改 → 写回必须在同一把锁里。** `post` 的追加也在锁内；锁外重写会把恰好在这一瞬间
  追加的那条心跳**覆盖掉** —— 它自己收到 ✓，板上却没有。所以 `prune` 全程持 `.lock`。

### 为什么按整段日期块搬，而不是按行数截

`board_entries()` 靠每段自己的 `## YYYY-MM-DD` 定位日期基准，搬走一整段不会让剩下任何一条的
时间戳算错；按行数随便截，剩下那些"没有日期段"的条目就会落到错误的基准上。
自测 [40] 里有一条专门检这个：搬完之后剩下那条的时间必须还解析成它原本的那一天。

## 参数调优建议

| 场景 | 建议 |
|---|---|
| 默认多 agent 开发 | `--interval 15 --stale-after 45` |
| **真 LLM agent（推荐）** | `--interval 15 --stale-after 90` —— 一次「模型思考+工具调用」往返实测 30~60s，45s 会被正常往返撞响（实测：某 agent 一次 read-user+ack+收尾花 53s，按 45s 报了警） |
| agent 动作粒度粗（单步 1~2 分钟） | `--stale-after 120`，并要求长任务用 hold |
| 快速冒烟测试协议本身 | `--interval 2 --stale-after 4 --ticks 5` |
| 只想观察不写告警 | `check --readonly` / `watch --readonly` |
| 心很宽的 agent（一次工具往返就可能连发多条心跳） | `init --rate-cap 0` 关掉心跳预算，或调到 120+ |

熔断阈值（`PINGPONG_*` / `POST_CAP`）是**源码里的常量**，不是 CLI 参数 ——
刻意如此：它们应该改一次就全局生效，而不是每个调用点各传一个值、最后没人记得当前是多少。
唯一例外是 `post_cap`，因为它跟"这块看板上 agent 的动作粒度"强相关，所以放在 `init` 上。

## CLI 细节（踩过的坑）

| 事项 | 行为 |
|---|---|
| `--dir` 位置 | 子命令**前后都可以**（`--dir X post …` 与 `post --dir X …` 等价）。靠给子解析器的 `--dir` 设 `default=SUPPRESS` 实现，否则子解析器会用 `None` 覆盖主解析器已解析的值。 |
| 目录来源优先级 | `--dir` > `$WORK_LOG_DIR`；两者都没有 ⇒ **退 2 并指路，不再猜默认落点**（2026-09-28 起；旧版落桌面，实测触发权限弹窗 + 两块板各说各话） |
| `serve` 端口被占 | 明确报错退出（`✗ 端口 8788 起不来：[Errno 48] … 换个端口：8789`），**不静默失败**。否则你会拿旧进程服务的另一块看板做验证（实测踩过）。换端口后务必核对 `/api/board` 的 `task` 字段。 |
| `--dir` 指向已存在的普通文件 | 直接报错**退出码 2**，不会炸出一堆 traceback |
| `--text` 以 `-` 开头 | 支持（如 `--text "- 我先停一下"`）。`main()` 会预先把这类值合并成 `--text=…`；但下一个 token 若是已知选项名（如 `--done`）则不合并，仍按"漏传值"报错。 |
| `--text` 传空串 | 拒绝（**退出码 2**）。空心跳等于没写，比不写更坏——它会骗过看门狗。 |
| `--stale-after < 1` | 拒绝（**退出码 2**）。设 0 会让所有 agent 立刻被判卡死。 |
| **stdout 行缓冲** | `main()` 入口统一 `sys.stdout.reconfigure(line_buffering=True)`。**这条是必须的**：后台跑 `watch` / `serve` 时 stdout 进管道或文件，Python 默认全缓冲，会出现"服务在跑但一个字都看不到"——实测 `watch` 跑 4 分钟、输出文件 0 行，`serve` 连自己打印的访问地址都看不见。 |
| `check --readonly` | 除了补建缺失的文件，不写任何东西（不落盘 state、不写告警）。 |
| `state.json` 损坏 | 记一条警告到 stderr，按空看板继续，不中断。（看板反解会把它补回来） |

## 用真实模型验收（selftest 覆盖不到的部分）

`selftest.sh` 只证明 CLI 本身没坏，**不证明真实模型会照协议走**。`scripts/llm_agent.py`
把 work-log 的动词暴露成 function-calling 工具，让模型自己决定说什么、问谁、等谁，
从而把「协商是模型真的做出来的」和「host 替它编排的」区分开。

```bash
python3 scripts/llm_agent.py --agent agent1 --board <dir> --base <url> --key <key> \
    --model <name> --peer agent2 --role "后端" --task "…" --max-steps 16 &
python3 scripts/llm_agent.py --agent agent2 --board <dir> --base <url> --key <key> \
    --model <name> --peer agent1 --role "前端" --task "…" --max-steps 16 &
```

实测踩到的现实约束（真端点、真模型）：

| 现象 | 数字 | 后果 |
|---|---|---|
| 单轮模型耗时 | 0.6s ~ 118s（同端点不同模型） | 默认 `--stale-after 45` **必然误报**，agent 想事情想 56s 就被判卡死。真机起步 90，慢模型 180 |
| 推理模型耗尽 token | `finish_reason=length` 且 `content` 为空 | 看着像"模型不听话"，其实是被截断。`max_tokens` 给 ≥3000 |
| 思考通道字段名 | `reasoning` / `reasoning_content` 都见过 | 流式解析只认 `content` 会得到"帧很多但正文为空"的假象 |
| 网关按模型限流 | `503 no_available_workers` | 同一端点有的模型可用、有的不可用；必须带重试 |

**驱动层自己的三个坑**（不是协议的锅，但会让你误判成"skill 不行"）：

| 症状 | 真相 | 修法 |
|---|---|---|
| agent 死在第 3 步的 `await`，日志里是没人接的 `TimeoutExpired` | 驱动层 `subprocess.run(timeout=120)` 与模型请求的 `await --timeout 120` 相等，子进程被自己人杀掉 | 驱动层超时 = 模型请求等待 + 90s 余量，并 catch 住 |
| post 被拒"text 不能为空"、reply"没有 #0 号提问" | 模型把参数套了壳：`{"arguments":"{...}"}` 或 `{"arguments":{...}}`，`json.loads` 一次得到的是壳 | 剥 str/dict 两种壳，再按工具的 `required` 字段找真参数 |
| agent 收到"成功"却基于错信息往下走 | 编号被壳吃掉 → `await --id 0`（合法语义："等任何新动静"）**返回成功**，agent 以为拿到了答案 | 校验必需字段，缺 `id` 就报错让模型重试，**绝不静默传 0** |
| 看板被"进入长任务"刷屏 | 驱动层每步都调裸 `hold` | 驱动层用 `hold --quiet`，只声明窗口不写条目 |

**自然的并发情形**：两个 agent 常会**同时**向对方提问（各自的 `ask` 交叉）。
这本身**不是** bug——只要两边分别 `reply`，两条交换就都能 `closed`，不会死锁。

要小心的是它的坏版本：**两边都先 `ask`、再当场 `await` 对方的回答**。
`reply` 是一个独立动作，谁先答谁就破环；但如果两个 agent 都被写成"问完就阻塞等答案、
等到才继续"，那谁也走不到 `reply` 那一步——这才是真的死锁环。
`await` 自己会在**下一轮扫描**时认出环并立刻退 5（不干等到超时），并留标记让对端也退出来；
等待图会把它标成 `[互相等待]`（自测 [43] 组 + [25] B 场景有回归用例）。
验收时要确认两条交换都被 `closed`，而不是只关了一半。


## 已知边界（诚实说明）

- 看门狗只能**发现**卡死并**告知**，不能杀进程、也不能自动重启 agent——它没有这个权限，
  也刻意不这么做。接管动作由在线 agent 或用户执行，脚本负责把"谁卡了、卡在哪、占着什么"
  三件事摊在看板上。
- 心跳是**自我申报**的，看门狗测的是「最近有没有人动过状态」，不是「有没有真的在推进」。
  三条具体的盲区：
  1. 不写心跳的 agent 会被发现，但"写了心跳其实没干活"发现不了——这靠正文质量约束
     （禁止"处理中"这类空话），不靠机制。
  2. `await` / `hold` 会持续刷新 `last_seen`（这是为了让"在等别人"不被误伤）。
     **这一类已被「等待图」补救**：等待关系现在被显式写进 `state.awaiting`，
     所以"等一个永远不会来的答案"（不可达等待）和"两人互等"（死锁）**能**被检出并告警，
     `await` 自己也会在对端收工时立刻返回 3（实测：60s 白等 → 0s 收手）。
     但**只有 `await` 的等待是已知的**：agent 若在等一个外部条件（等 CI、等下载、等端口），
     协议看不见，仍会被显示为健康。
  3. 方向错了但还在动（无限重试、做错的事）**部分**可测：心跳刷得过密会被心跳预算拦住，
     连续来回互相确认会被乒乓熔断拦住。但这两条都是**启发式闸门而非诊断** ——
     阈值到了只知道"这个模式看着像失控"，分不清"必要的深挖"与"空转"，
     所以必须留 `--force`，且不能拿它当进度结论用。
     真正的"做错的事"仍需要外部信号（git diff / 文件 mtime / 进程 CPU 占用），**目前没做**。
- **熔断会误伤，这是设计上的取舍**。阈值是固定的（6 轮提醒 / 12 轮停），
  一次真的需要 15 轮来回的深度协商会被拦下来。选择"多拦一次、让 agent 加 `--force`"
  而不是"放它烧完整个预算"，理由是前者只损失一次工具调用，后者损失一整轮 token 预算。
  如果这块看板上的协作天然话多，把常量调大或把 `post_cap` 设 0。
- **交流靠"拉"不靠"推"**：模型上下文只在它自己发起工具调用时更新，没有任何通道把消息
  推进正在跑的模型。`brief` 的增量探针挂在 `post` 的必经路径上来逼近推送效果，但若某个
  agent 长时间不调 `post`/`brief`，它就真的看不到别人说了什么。
- 因此这套东西适合「让协作过程可见 + 兜住明显的挂起 + 让协商有机制可依」，
  **不适合当作精确的进度监控**。
- 无 `fcntl` 的平台（Windows）会退化为无锁并打印一次警告：单进程使用无影响，
  多进程并发写不保证安全。
