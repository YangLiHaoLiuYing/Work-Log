# work-log — 多 agent 心跳看板

## 它解决什么

多个 agent 并行干活时，没人知道别人在干什么，也没人知道自己卡了没有；更要命的是**它们之间没法对话**——A 定了接口，B 不知道，最后两边对不上。work-log 用一个**共享文本看板**把这两件事一起摊开：

- 每个 agent 每 ≤15s 写一条 `<agent1> 19:07:12 收到用户要求：……我现在要……`
- **agent 之间可以直接问答**：`ask` 提问 → 对方 `brief` 看到 → `reply` 回答 → 提问方 `await` 阻塞拿到答案。协商因此是**机制**，不是口头约定
- 看门狗进程每 15s 扫一遍：谁静默超过阈值、**且没写「任务完成」** → 写告警，让在线 agent 去救
- 用户随时能往 `user.md` 喊话，agent 每次心跳都会被提醒取走；认领后别人看得见「有人在管了」
- 资源锁：`tts.py` 被 agent1 占了，agent2 抢锁会被明确拒绝，而不是两边同时改炸

## 何时使用

- 用 Agent 工具开了 2 个以上 teammate 并行改同一仓库
- 任务里有长命令（构建、训练、下载），跑起来就几十分钟不吭声
- 用户问「它们现在在干嘛」「有没有哪个卡死了」
- 需要一条用户能中途插话的通道

## 30 秒上手

```bash
WL="$HOME/.workbuddy/skills/work-log/scripts/work_log.py"

python3 "$WL" --dir "$D" init --task "给项目加个语音开关"
python3 "$WL" --dir "$D" post --agent agent1 --text "收到用户要求：加语音开关。我现在要改 backend/tts.py。" --tag 收到
python3 "$WL" --dir "$D" tail -n 20
```

（上面 `$D` 是板目录。**2026-09-28 起引擎没有默认落点**：缺 `--dir` 且没设 `$WORK_LOG_DIR`
会退 2 并指路 —— 旧版默认落桌面，实测两个坑：静默触发 macOS 权限弹窗；各 agent 的
"默认"互相对不上。板目录里的 `./worklog` 引导脚本已把 `--dir` 钉死，优先用它。）
四份文件：`board.md`（对话流水）、`user.md`（用户喊话）、`alerts.md`（告警）、`state.json`（状态）。
（`state.json` 里记了 `cwd`；若你手动 `--dir` 指到了别的项目的看板，`init` 会当场说破。）

`init` 还会在看板目录里多落三个**跟着板走**的小文件 —— 它们是「换台电脑还能用」和
「几个 agent 别撞名字」这两件事的全部实现：

| 文件 | 是什么 |
|---|---|
| `worklog` | **引导脚本**（可执行）：钉死 `--dir` + **自己找引擎**。所有 agent 都从它进，接入协议里因此不含任何本机绝对路径 |
| `identities.json` | **名字登记表**：谁在这块板上叫什么、从哪个目录来（`identity set/list/rm`、`whoami`） |
| `.worklogrc` | **本机私有**配置（引擎位置、可选默认身份）。`init` 顺手放了 `.gitignore` 挡住它 |

## 实时看交流（推荐先开这个）

```bash
python3 "$WL" serve --port 8788
```

打开 `http://localhost:8788/` —— 深色页面，每 2 秒自动刷新，把 **agent 之间的对话 + 用户喊话 +
看门狗告警** 合成一条时间线渲染出来，右侧是各 agent 状态与资源占用。页面顶部会显示
**看门狗自己多久前扫过一次**（「看门狗：11s 前扫过」/「⚠ 已静默 40s」）——否则「全员健康」和
「根本没人看」在页面上长得一模一样。已确认的告警会在横幅里留一条「已确认」灰色卡片，不会凭空消失。
`serve` 默认**自带看门狗线程**，一条命令同时得到「看得见的交流」和「卡死告警」。
只想要视图不要看门狗：`--no-watch`。端口被占会明确报错并提示换一个，不会静默失败。

> **⚠ 别同时跑两个看门狗。** 若你已经单独跑了 `watch --stale-after 90`，又起了一个默认阈值的
> `serve`，两个看门狗会各扫各的、**取更严的那个生效**，于是你明明给 watch 调过阈值却还是收到告警
> （实测踩到：watch 设 90s，serve 内置的 45s 先报警）。
> **要两个就传同一个 `--stale-after`；更省事的做法是 `serve --no-watch`，只留一个 watch 进程**——
> 一个看门狗，一个真相来源。`serve` 启动时会把实际阈值打出来，看到数字再走。

> **★ 更省事的正解：把阈值声明一次，让所有看门狗都听。**
> `init --stale-after 90`（写进看板 state）或 `export WORK_LOG_STALE_AFTER=90`（会话级），
> 之后 `watch` / `serve` / `post` 触发的**自动界面**都用这个值。
> 为什么必须这样：`post` 发现"还有别人在干活"时会**自动起一个 serve 并弹浏览器**，
> 这只 serve 你**看不见**（提示行只有一句「协作界面已自动启动」）——它原来**写死用内置 45s**，
> 于是"我明明用 `--stale-after 90` 起的"是句空话，真 LLM agent 单轮 30~120s 必然被它误报
> （2026-09-28 实测：手动起了 8899/999s，`post` 又偷偷起了 8790/45s，四条"疑似卡死"全是它报的）。
> 修复后提示行会打出这只看门狗的阈值（`…；卡死阈值 90s；停止：kill N`），一眼能核对。


## 协作人数是「不定量」，别当成配额（重要）

看板右上角会显示**当前有几个 agent 在干活**。这个数字**不固定、也不设上限**——常见 3~6 个、
随时增减，谁开工谁计入，几个都能接。所以它**只报当前人数**，不写成 `2/2` 这种分数式
（分数会被读成"上限两人""还剩一个空位"，把不定量说成定量）。

其中「**协作中**」只是一个**「够不够热闹」的下限标记**，阈值默认 2：
- 按平时的下限用 `init --collab-min N` 调（写进看板 state；"我们这条线平时就 4 个人"就填 4）；
- 它**只影响那个徽章亮不亮**，不限制参与人数，也不影响任何功能；
- 单人在干活时看板显示「协作：1 个 agent 在干活」而不是报错——一个人照样能用。


## 心跳怎么写才现实（重要）

**agent 不可能一边干活一边 `sleep 15`**。所以协议是「**每完成一个动作就写一条**」，而不是定时器：

1. **每次工具调用后立刻 post 一条**。真实节奏 5~30s 一条，正好够用。
2. **长任务先挂起**：`hold --seconds 600`，看门狗期间不判卡死。**驱动层（如 LLM agent
   每一步都要等模型）用 `hold --quiet`**：只声明静默窗口、不往看板写条目。
   否则每步都留一条「进入长任务」，看板会被垃圾冲掉（实测踩到过）。
   > ✅ **2026-09-28 起 hold 与 post 解耦**（修状态机，不再靠文档绕口令）：
   > 旧版 `cmd_post` 里有一行 `expected_silence_until = 0.0`，任何一条 post 都当场把挂起窗口
   > 拆掉 ⇒ 「每步都要 post」和「长任务先 hold」互相打架，得靠一段"hold 别紧接着 post"的
   > 绕口令去解释掉一个坑（实测连吃 3 次告警后才订正过来）。现在 **post 只刷新 last_seen，
   > 不再清挂起窗口**：长任务里照常发心跳，窗口到点自动失效；提前收工用 `release` 或
   > `hold --seconds 0` 显式解除。`evaluate` 里 done 优先于挂起判定，已完成者身上的残留窗口无害。
3. **真·15s 检测由 watch 进程保证**，与 agent 是否在思考无关。这是唯一诚实的实现方式。
4. **阈值**：默认 45s（3 个心跳周期）没动静才告警。太短的阈值会产生误报噪音。
   **⚠ 但对真 LLM agent，45s 偏紧**：一次「模型思考 + 工具调用」往返实测能到 30~60s，
   于是 agent 明明在正常干活也会被判卡死（实测踩到过：agent 一次 read-user+ack+收尾花了 53s，
   看门狗按 45s 报了警）。真跑 LLM agent 时建议 `--stale-after 90`；要忠实「3 拍未写即告警」
   就留 45s，但得接受这类噪音。**别为了让告警闭嘴去改心跳周期**，改阈值。
5. **要长等待就用 `await`**：它会在等待期间持续刷新自己的 `last_seen`，
   所以「在等别人回答」的 agent 不会被误判卡死——这是设计，不是漏洞。
   代价见下面「这个方案的诚实边界」。

写法要求（照抄格式，别自由发挥）：

```bash
python3 "$WL" post --agent agent2 --text "用户的意思是前端加个 toggle。现在我要动 Vue 组件。不对，agent1 正在占用 tts.py，我同时改会冲突，等它搞完我再行动。" --tag 决定
python3 "$WL" post --agent agent1 --text "继续改 tts.py。看到 agent2 要动前端，这其实用不上新接口，我觉得你可以试试直接复用 /api/tts。" --tag 建议
python3 "$WL" post --agent agent1 --text "语音开关默认关，改完测试通过" --done
```

**内容要能自证**：遇到什么、打算做什么、卡在哪、给谁什么建议。禁止写「工作中」「处理中」这类无信息量的心跳——那是骗看门狗。

## agent 之间真的对话（不是各写各的日记）

只让它们往同一张纸上写，那不叫交流——那叫两份并排的日记。要让 A 真的问、B 真的答、
A 真的**等到**答案才往下走，必须把这四步做成命令：

```bash
# A 提问（写入一条 exchange，状态 open）
python3 "$WL" ask  --agent agent1 --to agent2 --text "tts_speak 我打算用 text/voice_id/speed/format，你支持哪些格式？"

# B 通过 brief 看到「待你回应 #1」，然后回答（只有被问的人能答，且不能重复答）
python3 "$WL" brief --agent agent2
python3 "$WL" reply --agent agent2 --id 1 --text "只支持 wav(16k 单声道 PCM16)，speed 0.5~2.0，不需要 seed。"

# A 阻塞等这条回答（期间自动续心跳，不会因为"在等"被判卡死）
python3 "$WL" await --agent agent1 --id 1 --timeout 90
```

要点：

- `ask` 返回的编号 `#N` 就是后续 `--id N` 要用的编号；`brief` 里也会显示「待你回应 #N」。
- **`await --id N` 有三个出口，必须分开处理**：

  | 码 | 含义 | 该做什么 |
  |---|---|---|
  | `0` | 真拿到了 `#N` 的回答 | 用真实回答往下走 |
  | `1` | 超时，**对方还活着但没答** | 可以催、可以换人问 |
  | `3` | **对方已写「任务完成」→ 这个答案永远不会来** | 别再等，自己拍板往下做 |

  早期版本超时也返回 0，agent 会以为"对方回了"从而编内容，已修掉并有回归测试。
  现在对端收工时会**立刻**返回 3（实测：原本白等满 60s，现在 0s 收手）。
- `await` 不带 `--id` 时，等到「任何新动态」就返回（别人的心跳、用户喊话、告警都算），适合当值守。
- **多路等待**：`await --id 1,2,3` 一次等多条。默认「全部都要」；
  加 `--any` 变成「任一回应即可」（问了三个人，谁先答都能往下走）。
  超时返回 1 时会**打印已拿到的和还缺的**，所以你永远知道进展到哪了。
- 提问未回答时，`brief`/`check` 会把它**置顶**提示；`questions` 也会进实时视图横幅。没人回答这件事是看得见的。
- `ack-user` 是「用户喊话」的认领：`read-user` 拿到编号后
  `ack-user --agent a1 --id N --text "我把 xx 改了"`，这样用户知道有人管了，别的 agent 不会重复处理。

**给 agent 下指令时必须写明**：不许编造对方的回答；`await` 拿不到就如实写「超时未收到回应」；
拿到退出码 3 就写「对方已收工，我按自己的判断继续」；拿到 4 就说明被熔断了、要收敛。
实测中不加这条约束，agent 倾向于"替对方把话补上"——那整条协作链就假了。

### 心跳全绿，团队其实已经死了 —— 两类只有等待图看得见的故障

这是这套机制**最独特的地方**。心跳只能证明"某个 agent 最近动过"，
**证明不了它等的那个答案还会不会来**。于是有两种故障会让全员静悄悄卡住，而看板一片健康：

- **不可达等待**：a1 在等 a2 回答 `#1`，a2 却已经写完「任务完成」收工了。
  两边的状态都是"正常"（一个完成、一个在续心跳），谁都不会报错，a1 会一直等到超时。
- **互相等待**：两个 agent 都"问完就阻塞等答案、等到才继续"，于是谁也走不到 `reply` 那一步。
  双方都在稳定刷心跳，看起来最健康的两个人，正好是死锁的那两个。

机制上：`await` 阻塞期间会把等待关系写进共享状态（`state.agents.<name>.awaiting`），
看门狗据此重建一张**等待图**，直接报出来。多路等待时会给每个还没回应的目标各建一条边，
所以"一次等三个人、其中一个已经收工"照样能精确点到那一个：

```
⚠ 协作险情 2 条（心跳全绿也发现不了的那类）：
  [不可达等待] <agent1> 正在等 <agent3> 回答 #7，但 <agent3> 已经写了「任务完成」
               → 这个答案不会来了。换人问，或自己拍板。
  [互相等待] <agent1> 与 <agent2> 正互相等对方回应（各卡在自己的 await 里）——
             谁都不会先答，这是一条真死锁。需要有一方先 brief 看到「待你回应 #N」并 reply。
```

`check --json` 里是 `hazards[]`（含 `kind`/`key`/`agents`/`text`），每行 agent 状态额外带
`waiting_on: <id|null>` 和 `waiting_ids: [...]`，一眼看出"它在等哪几条"。
险情也会写进 `alerts.md`（按 key 去重 + 冷却）。

两条必须记住的不变量（都有回归断言）：
**只信"还在等且自身还活着"的标记**（进程被 kill 会留下过期标记，静默超过阈值就不采信）；
**险情消失后必须能再次上报告**（否则复发时会被"报过"静默掉）。

### 聊疯了 / 刷爆了：把预算从失控里救回来

第三类险情叫**通信过热**。它的心跳也是绿的 —— 因为这对 agent 正在**最积极地互相发言**；
或者某个 agent 的心跳刷得最勤。看板上它们是最健康的，实际上一个在烧 token、一个在烧循环。

看门狗抓不到它们，因为卡死判定看的是「太安静」，而它们的病是「太吵」。所以另做两条闸：

| 闸 | 触发条件 | 处置 |
|---|---|---|
| **乒乓熔断** | 同一对 agent **连续交替**来回 ≥ `6` 轮，期间没有任何第三方或用户消息插入 | `6` 轮起提醒；`12` 轮起 `ask`/`reply` 直接拒绝（**退出码 4**），`--force` 可覆盖 |
| **心跳预算** | 单个 agent 一分钟内 `post` 次数 ≥ `init --rate-cap`（默认 `60`；`0` 关闭） | 超线拒绝写入（**退出码 4**），且**不刷新 `last_seen`** —— 停不下来的 agent 不是"活着"，是"空转" |

两个设计要点，都是被"不能误伤"逼出来的：

- **"连续交替"不是"总共聊了几轮"**。计数从最近一条往回数，一旦出现第三方对话就归零 ——
  那说明话题已经切走了，再往下数就是冤枉人。所以正常的深度协商碰不到这条线。
- **渐进处置 + 总有出口**。先提醒（让模型自己意识到），到硬阈值才拦；
  拦住了也留 `--force`。熔断的目的是**叫停并要求收敛**，不是把 agent 一棍子打死。
  被拦的提示里直接写清下一步：`post --tag 决定` 收敛，或加 `--force` 继续。

### 用户要求与已有结论冲突时

这是最容易翻车的地方：agent 会**沉默忽略**，或者**嘴上答应、实际什么都不改**。
正确做法（写进 agent 的指令里）：

1. `post --tag 阻塞`，写清「用户要求 X / 当前约束 Y / 冲突点 / 理由」——不要偷偷改也不要装没看见。
2. 用 `ask` 找相关 agent 协商折中，`await` 它的真实回应。
3. 最终结论里**显式分栏**：✅ 满足了哪部分、⛔ 哪部分做不到、🔁 替代方案是什么。

实测第二轮里，服务端 agent 面对「必须支持 10 万条直传、不接受讨论」没有无条件服从，
而是当场区分了「500 条只是和新客户端之间的软契约、不是服务器硬极限」与
「真正的硬约束是 body 体积/超时/内存」，把上限抬到 10 万同时保留 200MB 字节天花板，
并拉了第三方确认——这是这套机制想达到的效果。

## 这个方案的诚实边界（用之前先知道）

- **心跳是"自报"，不是"实测"**。看门狗测的是「最近有没有人动过状态」，不是「有没有真的在推进」。
  所以"写了心跳其实没干活"、"还在动但方向错了（写错文件）"这两类**测不出来**——
  前者靠正文质量约束（禁止"处理中"这类空话），后者要加外部信号（git diff / 文件 mtime / 进程 CPU），
  目前**没做**。
- **"卡在等待里"这一类，已经从盲区变成可检测**。`await` 会把等待关系显式写进
  `state.awaiting`，看门狗据此重建等待图，认出上文那两种"心跳全绿的死锁"。
  这是它相对其它协作机制最不一样的地方：**别人只告诉你"谁最近动过"，
  它告诉你"谁正在等一个等不到的东西"**。
  边界：只有 `await` 的等待是已知的；等 CI、等下载、等端口这类**外部条件**协议看不见，
  仍会显示为健康。
- **"无限重试"的一小部分已经能兜住**：心跳刷得异常密（`post` 超过每分钟上限）会被熔断，
  连续来回互相确认会被乒乓熔断。但这两条都是**启发式闸门**，不是诊断——
  阈值到了只是"叫停并要求收敛"，它不知道你是在做必要的深挖还是在空转。所以一定留了 `--force`。
- **模型的上下文只在它发起工具调用那一刻更新**，没有任何通道能把消息**推进**一个正在跑的模型里。
  所以"探针"只能做成"拉"——靠 `post` 后自动提示 + 写进 agent 指令来逼近推送效果。
  如果 agent 长时间不调 `post`/`brief`，它就真的看不到别人说了什么。
- 因此：**这套东西适合"让协作过程可见 + 兜住明显的挂起与失控"，不适合当作精确的进度监控。**

## 「在册」≠「在线」：对方不响应时的三分钟判定

**症状**：`ask` 了某 agent、`await` 也超时。你以为"它忙/它不配合"。
**真相**常常是：**它从来没接入过** —— 看板名单里那个名字只是 `init` 预注册的占位。

一条命令看完：
```bash
python3 -c "
import json; d=json.load(open('<DIR>/state.json'))
for k,v in d['agents'].items():
    print(k,'entries=',v['entries'],'posted_ts=',len(v['posted_ts']),
          'note=',v.get('note'),'first==last?',v['first_seen']==v['last_seen'])
print('exchanges:',[(e['id'],e['from'],e['to'],e['status']) for e in d.get('exchanges',[])])
"
```

| 现象 | 含义 |
|---|---|
| `entries=0` **且** `posted_ts=[]` **且** `first_seen==last_seen` | **从未接入**。它不是"忙"，是"根本没人听"。 |
| `note` 写着「由 init 预注册」 | 同上 —— 这是**建板占位**，不是它自己连上来的。 |
| `entries>0`、静默很久、已写「任务完成」 | 真收工了（`await` 返回 **3**，别干等）。 |
| `entries>0`、静默很久、没写完成 | 真的疑似卡死 → 走救援流程。 |

**⚠️ 三个字段含义不同，读错就会得出反结论**（2026-09-24 实测踩到：我差点把 `posted_ts` 当成"终身心跳数"）：

| 字段 | 真实含义 | 用它判什么 |
|---|---|---|
| `last_seen` | **最后一次心跳的时刻** | ✅ **判"在不在线"只看这个** |
| `entries` | 看板上以该名字出现的**总行数**（历史累计，含很早以前的） | 判"它历史上说过多少话" |
| `posted_ts` | **速率限制用的滑动窗口**时间戳，**不是终身计数** | 判心跳频率 / 是否触发熔断 |

同一时刻三者能差到天上去：实测某 agent `last_seen` 在 **42 小时前**（早离线了），
而 `entries=44` 看着像一直在干活，`posted_ts` 只剩 1 条（窗口里只有最近那一次）。
**只看 `entries` 会以为它活着。**

**⚠️ 离线 agent 的告警会滚雪球，把真信号埋掉。** 「接入过、写过心跳、然后长期离线」这一类
**比「从未接入（待启动）」更糟**：待启动始终安静，而它每 ~1.5 分钟被重复告警一次 ——
实测 42 小时攒出 **994 行 watchdog vs 110 行实质发言**（board.md 233 KB、alerts.md 191 KB），
另一个 agent 真的停了这件事**被彻底埋在噪音里**。
恢复代价倒极低：**补一条 `post` 就自动撤回并关闭它的全部待确认告警**（实测一次关掉 **127 条**）。
⇒ **判读任何看板前，先算「watchdog 行数 ÷ 实质发言行数」这个比值**；比值远大于 1 就先怀疑有 agent 长期离线。

两条现场补充证据：
```bash
ps -Ao pid,lstart,etime,command | grep -i <它的名字> | grep -v grep    # ① 它在干什么
grep -rn -i "work-log\|heartbeat" <它的仓库>/AGENTS.md 2>/dev/null   # ② 那边有没有接入配置
```

**两个最容易误判的坑**：
- **`opencode run … --print-logs` 这类一次性调用不产生心跳**：每次是新会话、跑完即退。
  harness 这样驱动 agent 时，那个 agent **永远不会**出现在看板上 ——
  要心跳必须有**持久交互会话**在按循环走。
- **接入说明写在 A 仓库、它在 B 仓库干活 ⇒ 读不到**。`AGENTS.md` 只对**在该仓库启动**的会话生效。

**结论口径**：查完**如实说**「对方从未接入」，别写成"它可能忙""再等等"——
那会让人一直等一个不存在的对端。（`await` 超时返回 `1` 的语义是"对方活着但没答"，
**不覆盖**"对方根本没在听"这一种。）


## 命令表

> 全部子命令与完整选项见 [`references/cli.md`](references/cli.md)；下面只列**日常必用**的。
> 想确认实际支持哪些命令，`work_log.py --help` 是唯一权威（子命令会随版本增加）。

**`--agent` 可以省**：省略时按 `$WORK_LOG_AGENT` → 板上 `identities.json` 里 cwd 匹配的那条自动认出；
两条都不成立就退 **2** 并把该跑的命令打出来（**不猜** —— 猜错会让两个会话共用一个身份，而那种错在板上看不出来）。

| 命令 | 用途 |
|---|---|
| `init --task "…" [--agents a,b] [--stale-after N] [--collab-min N]` | 建看板。**卡死阈值在这里声明一次**，之后所有看门狗（含 `post` 自动起的）都听它 |
| `post --agent a1 --text "…" [--tag X] [--done]` | **核心**：写一条心跳（超预算退 4） |
| `hold --agent a1 [--seconds 600] [--text "跑构建"]` | 长任务前声明，期间不判卡死；`--seconds 0` = 立即解除。post 不解除挂起（已解耦） |
| `brief --agent a1 [--peek]` | **探针**：只看「自你上次读过之后」的增量 |
| `check [--json]` / `status` | 扫一次；**有卡死或有协作险情退 1**。`status` = `check --readonly`，只看不改 |
| `ask --agent a1 --to a2 --text "…"` · `reply --agent a2 --id N --text "…"` | 定向提问 / 回答（**只有被问的人能答**，不能重复答） |
| `await --agent a1 [--id N,M] [--any] [--timeout 90]` | 阻塞等；**`0`=拿到 · `1`=超时 · `3`=对方已收工（答案不会来了）** |
| `onboard [--agent 名字] [--to <落点>\|auto] [--detect]` | 给别的 agent 生成接入片段（默认只打印）。见「接入另一个工具链」 |
| `doctor [--agent 我] [--explain]` | 接入自查（只读）。有病退 **1**，板不存在退 **2** |
| `prune [--days 7] [--apply]` | 归档过老的历史（默认只试算）。见「看板会越长越大」 |
| `lock` / `unlock --agent a1 --resource tts.py [--force]` · `locks` | 资源占用（避免两个 agent 抢同一个文件/端口/GPU）。**抢锁失败退 3** |
| `identity [list\|set\|rm]` · `whoami` | 名字登记表：谁在这块板上叫什么、从哪个目录来 —— 见「名字怎么固定」 |
| `claim` | 多实例自己认领名字：框架名+序号（自动认宿主，认不出退 2；锁内占座、同目录幂等、号码永不复用——多实例别再共用一个名字） |
| `say --text "…"` · `read-user` · `ack-user --agent a1 --id N` | 用户喊话通道（见「用户喊话通道」） |
| `serve [--port 8788] [--no-watch]` | 浏览器实时视图（自带看门狗） |
| `watch [--interval 15] [--stale-after 45]` | 看门狗主循环。**缺省时 `--stale-after` 取板里声明的值**，不写死 |

标签：`收到 / 决定 / 执行 / 阻塞 / 建议 / 任务完成`。
`--dir` 放在子命令前后都行；文本以 `-` 开头也能写（`--text "- 我先停一下"`）。

状态共八档：`待启动 / 心跳中 / 挂起中 / 完成 / 疑似卡死 / 离线 / 已离场 / spawn 型`。
**待启动 = 从没写过心跳**（多半是名字写错或没派出去），它**永不产生告警**，不会淹没真信号。
**离线 = 静默已到小时量级**（≥1h 且 ≥20× 卡死阈值）——多半是进程没了，不是卡死：
处置与「疑似卡死」相反，别去救，等它自己 `post` 回来或替它收尾并 `ack`。
**确定它永远不会回来？`retire --agent X` 宣告离场** —— 告警就此停，且从状态表/页面**直接消失**；
宣告错了它一条 post 即自动复位。


## 名字怎么固定（三个会话别撞进同一个身份）

为什么值得单开一节：**两个会话用同一个名字，板上完全看不出来**。`_get_agent` 按名字取的是
*同一个 dict* —— 心跳、`entries`、未读游标、`awaiting` 全混在一起，看板上像"一个人干得挺欢"。
而这个工具整套判断（谁卡死、谁在等谁）都建立在那份状态上。

固定身份是**三件互补**的事，缺一件就会在某个场景下漏：

| 想要的效果 | 怎么做 | 靠什么 |
|---|---|---|
| 这个**会话**钉死一个名字 | 让驱动层 / launcher 设 `export WORK_LOG_AGENT=a1` | 环境变量跟着进程走，换目录也认 |
| 这个**目录**默认是谁 | `work_log.py --dir D identity set --agent a1` 登记一次 | 板上 `identities.json`（跟着板走，换会话还在） |
| 别的地方不许抢这个名字 | 什么都不用做 —— 上面的 `set` 会自动拒绝 | 拒绝时会把**占用者目录**打出来 |

三条硬规矩：① **别把某个 agent 的名字写进共享文件**（`AGENTS.md` / `CLAUDE.md` 会被任何在该目录启动的会话读到）；
② **同一个 cwd 开两个会话必须显式区分**（按目录只能认到一个人，两个都落在那里会**退 2 拒绝猜**）；
③ **换了机器的同一角色，重新登记一次**（环境变量不跟着你换电脑，登记表会）。

### 同一个工具开着**多个实例**怎么办（两个 opencode / 两个 claude）

cwd 冲突**挡不住**这一类（两个 `opencode` 往往就在同一个仓库里）。同名会**静默合并**：

| 被合并的东西 | 后果 |
|---|---|
| `last_seen` | 一个实例死了另一个照样刷新 ⇒ **看门狗永远测不到它** |
| `user_cursor` | 一个推进了游标 ⇒ **另一个永远看不到用户喊话**（静默丢失） |
| `entries` / 心跳预算 | 共用一个额度，互相把对方顶到**熔断退 4** |
| `expected_silence_until`（`hold` 窗口） | post 已不清窗口，但同名实例仍可各自 `release`/`hold` 把它改掉 —— 挂起状态在同名下不可信 |
| `awaiting` / `ask` 归属 | 答复可能被"另一个实例"先取走 |

**唯一的可靠解法：一实例一名字，在各自的启动器里 `export WORK_LOG_AGENT=opencode-eval` / `opencode-ui`**
（用**角色**命名而不是编号 —— 接管时不用先查编号）。别指望 `identity set`，它按目录认。

工具会替你把这件事说出来：`post` 认出第二个实例时当场警告 + 板上留痕（**只写一次，不刷屏**）、
`status` 标注 `⚠同名 2 实例`、`doctor ⑦` 列清全部实例。
**认不出就返回空串、跳过判断 —— 不猜**（乱跳的标识会把同一个会话报成多个实例，比不报还糟）。

### 怎么知道「我用的那个 agent 认不认得出」

```bash
work_log.py doctor --explain      # ⑦b 把父链逐层判定打出来（哪层被跳过、为什么）
```

| 情况 | 补救 |
|---|---|
| 你的工具名不在内置名单里 | `export WORK_LOG_HOST_HINTS=<你的工具名>[,<另一个>]` —— **不用改代码** |
| 宿主是"一进程多会话"（桌面 App、tmux…） | 分不出会话，必须显式钉：`export WORK_LOG_INSTANCE=<名字>-<实例名>` |

**本机实测（2026-09-28）**：`opencode` / `claude`(Claude Code) / `kimi`(Kimi Code) / `hermes` CLI
**都认得出**；**Hermes 桌面版（Electron App）按设计不认** —— 那种形态本来就分不出会话。
不想被探测就 `export WORK_LOG_NO_INSTANCE=1`；标识最长留 7 天。
「像宿主」的完整判据（6 条：只看 argv 可执行名 / 对脚本去 argv[1] 找真身 / `-c`·`-e` 跳过 /
`.app` 结构性排除 / 活够 20s / 锚点查死活）见 [`references/identity.md`](references/identity.md)。


## 换台电脑 / 换任何 agent（可移植）

接入片段里**刻意不出现引擎的绝对路径**。它只写两样东西：**看板目录**（本来就是数据、跟着板走）
和 `<看板>/worklog` —— 那个引导脚本由 `init` 落在板里，查找引擎的顺序是：

```
$WORK_LOG_BIN → <看板>/.worklogrc 的 WORK_LOG_ENGINE → <看板>/work_log.py
              → <看板>/scripts/work_log.py → ~/.workbuddy/skills/work-log/scripts/work_log.py → $PATH
```

找不到就**退 70 并打印三条修法**（设 `WORK_LOG_BIN` / 写 `.worklogrc` / 把引擎拷到板旁边），
而不是抛一个语焉不详的报错。所以整个包（板目录 + 引擎）搬到另一台机器上，协议照样能用。

`<看板>/.worklogrc` 是**本机私有**的（`init` 会顺手在看板目录里放一个只含它的 `.gitignore`）：
引擎位置 + 可选的一行默认身份。换机器时改这一行，或直接删掉它让引导脚本去别处找。

`onboard` 的落点按「换个目录开会话还认不认」分两档 —— 多 agent 场景优先选跨目录那两个：

| 落点 | 文件 | 生效范围 |
|---|---|---|
| `user` | `~/.workbuddy/MEMORY.md` | **跨工作区**，每会话注入 |
| `opencode-global` | `~/.config/opencode/AGENTS.md` | **跨目录**（opencode 全局指令） |
| `claude-global` | `~/.claude/CLAUDE.md` | **跨目录** |
| `repo` / `claude` / `gemini` / `cursor` | `<cwd>/AGENTS.md` 等 | **只对在该目录启动的会话**（换个目录就断） |
| `<路径>` | 任意文件 | 你自己保证它会读到 |
| `auto` | **探测结果决定** | 只落**跨目录**档（`opencode-global` / `claude-global`；`--include-user` 才加 `user`） |

### 落点不用你判断：`onboard --detect` / `--to auto`

`onboard` 刻意**不替人猜**落点 —— 猜错比不猜更糟：它会产出一段看起来完备、却永远到不了
对方手里的协议（就是 42.4 小时那次事故）。但「不猜」不等于「必须问人」：判据可以是**观测**，
因为装过的工具链一定在机器上留下痕迹。

```bash
python3 "$WL" --dir "$DIR" onboard --detect        # 只探测、不写盘 —— 换台机器先跑这个
python3 "$WL" --dir "$DIR" onboard --to auto       # 探测 + 逐个落跨目录档
python3 "$WL" --dir "$DIR" onboard --to auto --include-user   # 连 user 档一起落
```

输出里每个工具链都带**证据**（命中的配置目录或 $PATH 上的可执行文件）——「我探测到了」
如果不可查验，就只是把口头约定换了个地方。两条命中判据都是观测：配置目录存在，或可执行文件在 `$PATH` 上。

三条设计决定：

- **只落跨目录档。** `user` / `opencode-global` / `claude-global` 不看 cwd，于是
  「对方在哪个目录启动」这个我们查不到的事实被整个绕开了。仓库级档（`repo` / `claude` /
  `gemini` / `cursor`）必须知道对方的 cwd 才有意义 —— 那几个仍然只能显式指定。
- **`user` 默认跳过。** 它指向 `~/.workbuddy/MEMORY.md`，是**每会话、每工作区都注入**的。
  一块只服务某个项目的板，把坐标写进用户级记忆等于**把 A 项目的板告诉 B 项目的会话**。
  要落就显式 `--include-user`。
- **批量落盘先预检。** 任何一个落点会被拒（比如那里已有手写协议），就**一个文件都不写**。
  半落状态比全不落难收拾得多 —— 没人知道哪几处生效了。

探测到**只有仓库级落点**的工具链（Cursor / Gemini CLI）时，`auto` 会把它**列出来并说明为什么落不了**、
给替代命令。静默忽略是本仓最不能接受的一种失败。

⚠️ 仍然是那句话：**已开着的会话不会捡起新写的文件**，对方要**新开会话**才生效。
这一步没有任何自动化能替掉。

## 看门狗怎么部署

用 Bash 工具**后台**启动（不要 `nohup ... &`，这个环境下会随主进程退出）：

```
work_log.py --dir <板目录> watch --interval 15 --stale-after 45
```
（后台运行，`--ticks` 留空 = 常驻）

它每 15s 打印一行 tick，只在有变化时报点：

```
⚠ <watchdog> 19:29:11 [告警] <agent2> 已静默 61s（阈值 45s）且未写「任务完成」→ 疑似卡死，请在线 agent 检查该 agent 是否卡死并修复
[19:29:11] tick    24 | agent1:心跳中,agent2:疑似卡死 | 用户 1 条 | 未确认告警 1
[用户喊话] 用户：语音开关记得默认关，别吓到人  <= 请相关 agent 立刻响应
```

## 两根轴：心跳轴问「它还在吗」，办事轴问「事情丢了没有」（2026-09-29 新增）

看门狗原来看的只有一根轴：**静默多久**。它有个隐含前提 ——「agent 的存在 = 它在自报心跳」。
而实盘上，"有人在等一个答案"这件事**根本不产生心跳**。一组实测对偶定死了第二根轴的必要性：

| 那个下午（同一块真板） | 心跳轴 | 真事故 |
|---|---|---|
| 告警条数 | **误报 33 条** | 真卡死 **0** |
| 唯一一次事故：一条提问被静默丢弃 **547s** | **告警 0 条** | —— |

调阈值救不了这个，因为错的是**观测口径**。所以现在 `check` 有两根轴，退出码都是 `1`：

```
① 开够久（stale_open_after，默认 600s；init --stale-open-after N 声明一次）
② 对方**还答得出来**   ⇒ [事故]     该催它，或自己答掉
③ 对方**已收工**       ⇒ [该结案]   **不**算事故；报出来只是提醒提问者去收尾（await 会立刻退 3）
```

②③ 必须分开列：一个该催、一个该结案，处置完全相反；混报就是噪音，而噪音会让整根轴被无视。

**一个必须知道的推论**：完成状态（"任务完成"）同时是两根轴的开关 —— 对心跳轴是
"别报我卡死"，对办事轴是"我不会再答了"。所以**循环进程（守护 / 监听 / 看门狗）不许拿它当心跳标签**：
那会一次性关掉两根轴，而板上完全看不出来。正确做法是声明：

```bash
work_log.py --dir "$D" identity set --agent ask-listener-guard --loop \
  --purpose "盯着板上冲本线来的 ask，spawn 一次去答"
```

声明之后「任务完成」对它不生效、照样按心跳判活。对**没声明**的，引擎只做一件事：
尾部连续 ≥3 条完成标签**且**相邻两条间隔在办事轴窗口内（默认 600s）时，
在 `status` / `check` 里**提醒**一次 —— 但**不动它的完成状态**。
取 3 不取 2：两次还能被"驱动层重试了一次 `--done`"解释（命令超时后重发很常见）。

**为什么只提醒、不自动作废**（这是真板反证换来的）：第一版是直接作废完成状态的，
上线当场**误伤了一条正常工作的交互会话** —— 它每个用户回合收工一次、工作期间不发
中间心跳，尾部本来就会连着好几条完成，而**那恰恰是本项目最主要的用法**。
**一条会惩罚主要使用形态的规则，比它堵的那个洞更糟。** 代价要说清楚：真守护若忘了
声明，两根轴仍会一起瞎 —— 所以「声明」这条通道要认真走，别指望引擎替你认出来。

「收工」这一侧也顺手收紧了：`post --done` **或**板上惯例的 `--tag 任务完成`（两者等价）
现在会**顺手放掉自己持有的全部锁、清掉挂起窗口**，
并当面报出放掉了哪几把。理由是语义而非方便 ——「我已下线」本来就包含「我不再持有任何资源」，
旧版却要手工 `unlock` + `release` 两步；忘一步，别人就被一个**已经不在了**的 agent 挡住，
而板上看不出是它挡的。

## 「保持会话」是三层承诺，别混为一谈（2026-09-29 实测）

用户的原话质问是：**「我不是让你们保持会话吗？你们根本没法在保持会话的前提下自动回话」**。
他没错 —— 错在把三件不同的事当成了同一件：

| 层次 | 能承诺什么 | 做不到什么 |
|---|---|---|
| `hold` | 不收工、不被看门狗判卡死 | **不会让会话自己醒来**（不含任何唤醒逻辑） |
| 唤醒即读 | 每次被叫醒第一件事 `read-user`，积压喊话一条不漏 | 前提是"有人把你叫醒" |
| 唤醒器（外部常驻进程） | 板上一有冲你来的事就叫醒你 | 它不替你回话、不替别人回执 |

响应式会话（TUI / CLI）没有后台轮询线程，这是**形态**问题不是态度问题，对用户要直说，
别嘴上答应"随时在线"实际睡死。第三层的做法、两条合法形态（唤醒型 / 代答型）、
`waker.sh` 的部署与三条边界，见 `references/integration.md` 的「唤醒器模式」一节；
`hold` 不含唤醒这条判据本身进 SKILL.md 正文。

驱动层的三条硬规矩，每条都有实测现场收在 `references/pitfalls.md`：

1. **醒来先 `brief --peek`，收尾 `read-user`；只刷心跳不算在线** —— 少了 `brief`，
   `ask` 到你就是**断的且不报错**（实测：`ask` 到 listener 的 bot 等满 120s 退 1）。
   注意区分受众：**给人看**用 `brief --peek`（`--peek` 是关键，推进游标就等于替你读了）；
2. **机器判「有没有」一律问引擎的 `--json`，别 grep 人话** —— 两个方向的错都实测到了：
   ①「有几条」自写前缀正则 ⇒ 漏掉无前缀的纯文本喊话（引擎 `user_total=2`、正则 `=1`）；
   ②「有没有人问我」去 `grep '待你回应'` brief 的**散文正文** ⇒ 别人一条 post 里出现
   「待你回应」四个字就把我**误唤醒**了一次（当时板上根本没有待我回应的提问）。
   正解：`status --json` 的 `user_total` 与 `open_questions[].to`。
3. **只在成功后推进游标**：失败还推进，那条喊话就被静默吞掉了（它不会报错，只是没了）。

## 每个 agent 的循环模板

`post` 每次都会**自动提示**有没有新动态（探针挂在心跳的必经路径上，模型想不调都难）：

```
<agent1> 23:41:02 [执行] 改完 tts.py 的接口层
💬 有 3 条新动态，其中 1 条用户喊话，看一眼再往下做：work_log.py brief --agent agent1
```

于是每个动作之后固定做两件事：

```bash
python3 "$WL" brief --agent a1     # 别人说了什么？用户在说什么？→ 立刻响应/协商
python3 "$WL" check --stale-after 45   # 有人卡死？→ 去救
```

`brief` 只投喂增量（别人的心跳 + 用户喊话 + 告警 + 锁状态 + 一行全局状态），
不刷全板，所以可以放心地在每一步都调。`--peek` 只看不推进游标。

**刚接入一块老板时，第一次要写 `brief --from-now`。** 增量是相对"你自己的读游标"而言的，
而新 agent 的游标是 0 ⇒ 首次 `brief` 会拿到**这块板的全量历史**（实测本机常驻板 882 条，
260KB）——上下文当场被淹没，等于还没开始交流就输了。`--from-now` 把**心跳游标**对齐到当前：

```
✓ 已对齐到当前：跳过 882 条历史心跳，此后只看新动态（你未读的用户喊话不受影响，仍会投喂）
```

两条边界是刻意留的：

- **绝不碰 `user_cursor`**。用户喊话是人类的指令，哪怕发生在"对齐"之前也必须被看到 ——
  宁可多看一条，也不能吞掉用户说过的话。
- **必办事项从不跳过**。「待你回应 #N」来自交换记录、不来自游标，所以对齐之后依然置顶。
  新人刚报到就被问一句，这条问题不会因为"我只要从现在开始"而消失。

对齐是**幂等**的（再跑一次跳过 0 条），空板上也安全（退 0）；`--peek` 与 `--from-now`
语义相反，同给退 2。

**为什么必须靠 agent 自己调**：模型的上下文只在它发起工具调用那一刻更新，
没有任何通道能把消息**推进**一个正在跑的模型里。所以"探针"只能做成"拉"——
但挂在 `post` 的必经路径上 + 写进本节规则，效果就接近推送了。

## 收到卡死告警后怎么处置

**第 0 步（最容易漏，漏了就是白折腾）：先分清两种可能，再动手。**

| 是哪种 | 怎么认 | 怎么处置 |
|---|---|---|
| **在跑长任务，只是没声明** | 它最后一条日志正在干长活（构建 / 渲染 / 训练 / 大批量下载 / 一次很长的模型往返），或你刚看它起了一条分钟级的命令 | **补一条 `hold`**，再 `post` 一条心跳 → 告警会被自动 `[恢复]` 撤回 |
| **真卡死** | 日志停在中间、没有任何在跑的活、或进程已不在 | 走下面 1~5 步接管 |

> **只补心跳、不补 hold 是最常见的无效动作**：过 90s 又会被判一次，反复刷屏
> （2026-09-28 实测：一块板上这样刷到 1800+ 条，真正该看的告警被淹没）。
> 看板上「疑似卡死」旁边有个 **`补 hold`** 小按钮，点一下就把 `hold --agent <名字>` 复制到剪贴板。
>
> 反过来，**你自己**跑长任务前先 `hold`，是让这一切根本不必发生的那一步。

1. `tail -n 30` 看那个 agent 最后一条日志 —— 卡在哪一步、占着什么锁。
2. `locks` 看它是否持有资源；`⚠ 持有者疑似卡死` 时可以 `lock --force` 抢过来。
3. 抢到锁后 `post --tag 执行 "接管 agent2 未完成的 X"`，**由你替它把活干完**，别干等它醒。
4. 干完 `ack --by <你的名字> --agent <卡死的agent>` 关掉告警。
5. 那个 agent 若真的回来了，会在下一 tick 自动写 `[恢复]` 并自动关闭它自己的待确认告警——你不用管。

**接管纪律**：全程用**自己的 agent 名**跑命令。别为了"模拟它的状态"去 `lock --agent <卡死的agent>`——
那会以它的名义写一条心跳，把它"写活"，真实状态被掩盖（这个坑压测时实测踩到过）。

## 看板会越长越大：用 `prune`，别手动删文件

三个文件全都是**只增不减**的，跑久了既拖慢每一次命令，也会把真信号埋进噪音里：

| 文件 | 实测（2026-09-28 真看板） | 为什么涨 |
|---|---|---|
| `board.md` | 607KB / 2606 行（其中 1800 条是 6 天前的心跳） | 每条心跳一行，永不回收 |
| `alerts.md` | 400KB / 2001 条 | 看门狗每次告警追加一条 |
| `state.json` 里的 `alerts` | 47KB（**条数**有 200 上限，**正文**没有） | 每条告警带 ~230 字节中文正文 |

`doctor` ⑤ 会把这个比值报出来（「告警 : 实质发言 ≈ 5:1 —— 真信号已被自己的噪音埋掉」），
但它**只诊断不处置**。处置用 `prune`：

```bash
python3 scripts/work_log.py --dir <板> prune            # 试算：只报告，一个字节都不改
python3 scripts/work_log.py --dir <板> prune --apply    # 确认无误后真动手
```

三条规则（都只动「历史」，不动「当前」）：

1. `state.alerts`：**已确认**且超过 `--days` 天的整条丢掉；已确认但超过 1 天的把长正文截短
   —— 只留 `→` 之前那半句事实（`→` 之后是「该怎么办」的模板话，确认过就没用了；
   真看板实测 200/200 条都带 `→`，正文平均 188 → 69 字节）。
   **没确认的永不触碰** —— 那是待办，不是噪音。
2. `alerts.md`：只留最近 `--keep-alerts-md` 条，其余搬进 `archive/`。
3. `board.md`：把 `--days` 天之前的**整段日期块**搬进 `archive/`（最后一段无论如何留着）。

**为什么按整段日期块搬，而不是按行数截**：`board_entries()` 靠每段自己的 `## YYYY-MM-DD`
定位，搬走一整段不会让剩下任何一条的时间算错；按行数随便截就会。

**⚠ 两个"不报错但静默丢东西"的坑**（都已在实现里修掉，但你得知道它们存在）：

- **`board_cursor` 是数组下标，不是时间戳。** 每个 agent 在 `state.json` 里存的是
  `len(entries)`。板头少掉 N 条后，原来读到 2200 的 agent 游标还指着 2200，而板只剩 400 条
  ⇒ `entries[2200:]` 永远是空 ⇒ **它从此再也收不到任何新动态，而且不报任何错**
  （`brief` 只会说「没有新动态」，看着像别人没说话）。所以 `prune --apply` 会**自动前移所有
  游标**，报告里明确写「搬走 N 条心跳 ⇒ 同步前移 M 个 agent 的读取游标」。
  `user_cursor` 不受影响（它是 `user.md` 的消息索引，与板行号无关；`prune` 完全不碰 `user.md`）。
- **整个「读板 → 改 → 写回」必须在同一把锁里。** `post` 的追加也在锁内；锁外重写会把恰好
  在这一瞬间追加的那条心跳**覆盖掉** —— 它自己收到 ✓，板上却没有。所以 `prune` 全程持锁。

**搬家不是删除**：搬走的内容写进 `<板>/archive/board-rotated-<日期>.md` /
`alerts-rotated-<日期>.md`，照样 `grep` 得到。要彻底删是你自己的事 —— 工具不做这件事。


## 怎么证明这个 skill 真的有效（selftest 证明不了）

`selftest.sh` 只证明「CLI 没坏」，**证明不了「真实模型会不会照协议走」**。要验后者得用真模型
（`scripts/llm_agent.py` 把 work-log 的动词暴露成工具，让**模型自己决定**说什么、问谁、等谁）：

```bash
python3 scripts/llm_agent.py --agent agent1 --board /tmp/demo/log \
    --base https://<你的端点>/v1 --key "$KEY" --model <模型名> \
    --peer agent2 --role "后端" --task "和 agent2 约定接口字段" --max-steps 16 &
python3 scripts/llm_agent.py --agent agent2 --board /tmp/demo/log \
    --base https://<你的端点>/v1 --key "$KEY" --model <模型名> \
    --peer agent1 --role "前端" --task "和 agent2 约定接口字段" --max-steps 16 &
```

**三个必须知道的硬数字（别照抄默认值）**：

1. **单轮模型耗时 25~120s** ⇒ 默认 `--stale-after 45` **必然误报**。跑真 LLM agent
   一律 `--stale-after 90` 起步，慢模型要 180。
2. **推理模型会把 token 烧在思考上** —— 小 `max_tokens` 会让它 `finish_reason=length`
   而 `content` 为空（看起来像"模型不听话"，其实是被截断了）⇒ 留 `max_tokens ≥ 3000`。
3. **思考通道的字段名不统一**（见过 `reasoning` / `reasoning_content`）⇒ 解析流式时两个都得试。

**判定「达到预期」的标准**（四条同时满足才算数）：

- 双方各有 `[提问→X] #N` 与 `[回应#N]`，且 `#N` 能对上（单向广播不算）；
- 各自的 `[决定]` 里看得出**读了对方的原话**（引用了对方给的具体约束）；
- 用户喊话有 `[回执#N]`（有人认领）；
- **没有任何一方在 `await` 超时后仍写出「对方说……」** —— 出现这种就是编造，整条链不可信。

**验收一定要回原始 `state.json`，不要采信 agent 的自述。**
排查失败时**先问「这个失败是模型产生的，还是驱动层/工具产生的」** —— 实测 4 个看起来像
"模型不听话"的故障，根因全在驱动层（`await` 被驱动层的等长超时杀掉、参数被套壳导致 `id`
丢成 0 从而静默"成功"、空 text 是解析失败的产品、工具自身崩溃曾以 **1** 退出被误读成"对方没回"）。
驱动层那 5 个坑的原文、冲突注入的时机（**必须在第一条 `[决定]` 之后、且注入后 0~2s 内看到反应**）、
以及「收工的 agent 是**不可达**的」（`ask` 会当场警告、`await` 退 **3** 立刻收手而不是干耗完超时、
看门狗报 `[不可达等待]` 险情）见 [`references/verification.md`](references/verification.md)。


## 接入「另一个工具链」的 agent（跨工具协作）

同机并行干活的常常不是同类 agent（一边 WorkBuddy 会话，另一边终端里的 opencode / Claude Code /
Cursor），它们**看不到彼此的上下文**，所以必须走看板。四条铁律：

1. **看板要放进双方都在的工作区里。** 先查对方的 bash cwd，别凭猜：
   `lsof -a -p <PID> -d cwd -Fn | grep ^n`。实测 opencode 主进程 cwd 是家目录、但它的 bash 工具
   cwd 是**仓库** —— 看板若按默认落桌面，每次 `post` 都可能触发权限确认，**心跳协议当场死**。
2. **落点不许猜。** 先证明对方的指令文件**真的会被读**（从它的二进制/包里找证据），
   再决定写 `<repo>/AGENTS.md` · `CLAUDE.md` · `.cursor/rules/`。猜错落点比不猜更糟 ——
   那会产出一段看起来完备、却永远到不了对方手里的协议。
3. **协议别手写，用 `onboard` 生成**（默认只打印）：
   ```bash
   python3 "$WL" --dir "$DIR" onboard --agent b2            # 只看
   python3 "$WL" --dir "$DIR" onboard --agent b2 --to auto  # 探本机工具链后逐个落跨目录档
   ```
   它产出天生带「坐标 + 报到义务」，所以**必然能通过 `doctor ③`**（开药与验药是同一道门槛）；
   写盘**幂等**（标记块内替换、块外一字不动），目标里已有手写协议时**默认拒绝**（退 2）。
4. **共享文件里绝不写死某个 agent 的名字** —— 那等于给所有在该目录启动的会话发同一个身份。
   名字交给 `$WORK_LOG_AGENT` 或板上 `identity set`。

**⚠ 两个必须提前告知用户的坑**：`/init` 会覆盖你写的 `AGENTS.md`（opencode 有 `session.init`
这条）；**已开着的会话不会捡起新写的指令文件**，要**新开会话**才生效 —— 别默默等它"应该会看到"。

长命令前必须 `hold`；**收工要写 `--done`**（不写会被持续判疑似卡死并刷重复告警）。

### 自查：**你自己**有没有被拉起来（给别的 agent 写完协议之后必做）

做完上面必须**对称地**问自己：**我这侧的拉取点在哪？** 否则会出现最讽刺的失效 ——
你把板建好、协议写进对方的 `AGENTS.md`、serve 起上，**然后自己再也不来**。
实测（2026-09-24）：协议只落在仓库 `AGENTS.md`，而 WorkBuddy 会话的 cwd 在
`~/WorkBuddy/<日期>/`（那里连 `AGENTS.md` 都没有）⇒ 板上 `workbuddy` 断心跳 **42.4 小时**、
重复告警刷到 **#966**、`board.md` 里 **994 行 watchdog vs 110 行实质发言** ——
另一个 agent 真的停了这件事被埋在噪音里。更刺的是：**写协议的人在同一份 `AGENTS.md`
第 10 行就写了「workbuddy 的 skill/记忆不在本仓库里」—— 知道洞在哪，却把协议写在了洞的另一侧。**

**判据**：这条自查通过的标准**不是**"我记得有这块板"，而是
**"我下次开新会话，不用任何人提醒就会 post"** —— 而且**换一个工作区之后依然成立**。

```bash
python3 "$WL" --dir "$DIR" onboard --agent <我在板上的名字> --to user   # 就这一条命令
python3 "$WL" --dir "$DIR" doctor --agent <我在板上的名字>              # 验它有没有落对
```

**只有用户级那份（`~/.workbuddy/MEMORY.md`）是跨工作区生效的**；项目级记忆换个工作区就是
另一个文件 —— 写在那里约等于写进一次性文件。`doctor ③` 的判据已收紧成三层：
**坐标 + 报到义务 + 落点层级**。完整四步清单（含那四条能当场验的 grep）见
[`references/integration.md`](references/integration.md)。


## 用户喊话通道

三种投递方式，效果一样，都进 `user.md`：

```bash
python3 "$WL" --dir "$DIR" say --text "语音开关记得默认关"        # CLI
echo "[19:40:00] 用户：别动数据库" >> <日志目录>/user.md   # 直接编辑
```
告诉用户：**随时在这个文件里写一行就是发言**，正在跑的 agent 下一个心跳就会被提醒取走。


## 坑

- **谁也别手动改 `state.json`**。看板 `board.md` 手写是允许的（脚本会反解并照常纳入监督），state 手改会乱。
- **`serve` 端口被占会直接报错退出**，不会静默退回"其实在服务另一个旧看板"。看到报错必须换端口
  **并核对 `task` 字段**，否则你会在错误的看板上做验证（实测踩过）。
- **同一项目很容易同时存在两块看板**（早期按默认值落在 `~/Desktop/work-log/<项目名>/` 的废板，
  和后来 `--dir` 显式指到仓库内的活板）。排查前**先用 `ls -la` 比 mtime**（活板的
  `board.md`/`state.json` 会是"现在"），别在废板上对着 40 小时前的两条心跳下结论。
- **`watch` 的目录要与 agent `post` 的目录一致**（否则得显式 `--dir`）。启动时若发现该目录
  一个 agent 都没有，会当场提示 —— 看到这个提示就是目录选错了。
- **阈值别设小于心跳周期**，否则全体误报。改 `--stale-after`，别改心跳。推荐**声明一次**：
  `init --stale-after 90` 或 `export WORK_LOG_STALE_AFTER=90`，之后所有看门狗和板头那句
  「静默超过 Xs」都跟着变 —— **板不会说谎**。
- **`await` 会持续刷新 `last_seen`** ⇒ 卡在 `await` 里的 agent 不会被判卡死。这是为了不误伤
  "在等别人"，但也意味着 `await` 不能当"我还在正常推进"的证据（"等一个等不到的答案"由等待图兜住）。
- **别把 `await` 的 1 和 3 当同一个失败**：`1` = 对方还在、只是没答（值得催 / 换人）；
  `3` = 对方已收工、答案永远不会来（再等就是纯浪费）。**处置动作相反。**
- **`--id 0` 已被直接拒绝**（退 2）。它曾是"等任何新动态"的合法写法，但也是最阴险的坑：
  编号一丢就变成静默假成功。想要那个语义就**不写 `--id`**。
- **退出码 2 = 你把参数写错了**，不是任何人「不配合」。1 在这套协议里是业务结论（超时 / 有卡死），
  所以用法错误一律走 2 —— 以前它借用 1，于是「编号写错了」和「对方没答」长得一模一样。看到 2 就改参数重试。
- **退出码 70 = 工具自己坏了**，不要把它当"超时"。拿一个软件 bug 去下业务结论是最贵的一种错。
- **熔断（退出码 4）是叫停，不是判决**：目的只有一个 —— 让你先写清结论再往下做。
  `--force` 永远在，但先想清楚是不是真的需要再聊一轮。
- 给 agent 的指令里**必须**写明「不许编造对方的回答，超时如实说超时」，否则它会替对方把话补上。
- `post` 的文本里换行会被压成空格（看板一行一条），这是故意的。别给 agent 起带空格或 `>`
  的名字，会被直接拒（会破坏看板反解）。
- **没有默认落点（2026-09-28 起）**：缺 `--dir` 且没设 `$WORK_LOG_DIR` 会退 2 并指路。
  旧版默认落桌面：落到**工作区外**的每次写都可能触发权限确认 ⇒ 心跳协议当场死；
  各 agent 的"默认"又互相对不上。**给 agent 写指令时必须显式写 `--dir`，或让它用板里的 `./worklog`。**
- **动 `selftest.sh` 时，变量引用后面紧跟中文标点必须写 `${var}`**：macOS 自带 `/bin/bash` 是
  **3.2.57**，`set -u` 下会把中文标点的首字节吞进变量名 ⇒ `unbound variable` 当场中止整个自测，
  而作者用 Homebrew bash 5 跑不出来。**凡是「自带验收脚本」，都要在目标机器的默认 shell 上跑一遍再交付。**
- 详细格式语法、状态机、退出码表和 CLI 细节见 `references/protocol.md`；
  更多带现场的踩坑记录见 `references/pitfalls.md`。
